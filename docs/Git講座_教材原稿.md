## 01｜① 達成目標｜この講座でできるようになること

**このページの結論：** Gitの学習目標は、**変更を記録・比較・復元する仕組みを自力で説明し、操作できること**。

### PART 01 — ゴールは「操作の意味が分かる」こと

この講座の目標は、Pythonのコードを編集したときに、Gitがその変更をどう把握し、どの操作で履歴に保存するのか説明できることだ。また、ブランチを使って改善を試し、問題があれば過去の状態を確認できるようになることを目指す。

### PART 02 — 修了時にできること

- GitとGitHubの違いを説明できる
- 作業ディレクトリ・ステージングエリア・リポジトリの役割を説明できる
- status・diff・add・commit・logを目的に応じて使える
- ブランチの作成・切り替え・統合を説明できる
- 過去のコードを比較し、安全な方法で戻せる
- MLflowのRun IDとGitコミットIDの違いを説明できる

### PART 03 — 学び方

図解・操作例の順に確認し、分からなければ一つ前のページに戻って構いない。ブラウザ内の疑似演習ではPCのGitを実際には操作しない。実コマンドは自分の練習用フォルダで試す。

## 02｜① 達成目標｜この講座で扱う範囲

**このページの結論：** **Gitはコードの履歴を担当**。モデル・実験結果・環境情報は別の管理方法と組み合わせる。

### PART 01 — 4つの技術は何を管理する？

**図解（compare）：**

1. **Git** — ソースコードと変更履歴
2. **Docker** — プログラムが動く環境
3. **pytest** — 処理が期待どおり動くか
4. **MLflow** — 実験条件・精度・学習済みモデル
Gitですべてを保存するのではなく、役割を分担する。

### PART 02 — 開発で使う技術の役割分担

| 対象 | 主な管理方法 | Gitだけで十分？ |
| --- | --- | --- |
| Pythonコード・テスト・設定ファイル | Git | はい（通常） |
| 学習条件・評価指標・保存モデル | MLflow | いいえ |
| 実行環境・OSライブラリ | Docker・依存関係固定 | いいえ |
| 大量の学習データ | データストレージ・DVC等 | 通常はいいえ |

### PART 03 — なぜ役割を分けるのか

例えば学習済みモデルの重みは巨大になることがある。コードと同じ方法でモデルのバイナリファイルを何度もGitに積むと、リポジトリが膨らみ、履歴管理も扱いづらくなる。Gitはコードの履歴に集中させ、実験結果はMLflowへ、環境はDockerへ分担させる。

### PART 04 — 前提知識

Pythonのファイルを作成・保存したことがあれば進められる。ターミナルの経験がなくても、コマンドの意味を1つずつ説明する。

## 03｜② 目的｜上書き保存だけでは困る理由

**このページの結論：** **上書き保存だけでは過去のコードを追跡しにくい**。Gitは変更前の状態へ戻る手段を提供する。

### PART 01 — Gitがある場合の考え方

1. **最初の状態** — 動くコードを記録
2. **改善** — 新しいコードへ変更
3. **比較・復元** — 過去と現在を追跡
Gitが記録するのは過去のファイル状態とその履歴だ。モデルの精度そのものは自動で記録しない。

### PART 02 — 変更前に戻したくても、ファイルを上書きしている

`train.py`に特徴量を追加して保存すると、通常は新しい内容がファイルに残る。前のコードを保存していなければ、「どの行を変えたか」「以前のコードはどうだったか」を簡単には確かめられない。

### PART 03 — ファイル名にv1・v2を付ける方法の問題

`train_v1.py`、`train_final.py`、`train_final2.py`のように複製する方法では、どのファイルが正式版か分かりにくくなる。変更理由や、複数ファイルの組み合わせも記録しづらくなる。

### PART 04 — この時点ではコマンドを覚えなくてよい

「コードを変更したとき、以前の状態を安全に取り出せるようにしたい」という問題意識がGitを学ぶ出発点だ。

## 04｜② 目的｜複数の作業を並行して進める理由

**このページの結論：** **ブランチは完成済みのコードを守りながら、別の改善を進めるための仕組み**。

### PART 01 — 完成版と改善版は別の履歴を進む

**図解（branch）：**

1. **main** — A → B → E（動作確認済み）
2. **feature** — B → C → D（モデル改善中）
Bの時点から別々に進み、完成後に統合できる。

### PART 02 — すべて同じコードで作業すると混ざりやすい

「モデルの特徴量を追加する」変更と「画面を修正する」変更を同時に進めると、途中の不完全なコードが混ざることがある。どちらか一方だけを取り込んだり、元に戻したりする作業も複雑になる。

### PART 03 — ブランチで作業の流れを分ける

Gitでは、同じ履歴から新たな開発の流れを始められる。例えば `main` を動作確認済みの版として残し、`feature/add-feature` で新しい特徴量を試す。改善を確認した後にmainへ統合できる。

### PART 04 — 作業の分岐イメージ

```text
A --- B ------------------- M   main
       \                 /
        C --- D ----------     feature/add-feature
```
A・B・C・D・Mは説明用のコミットだ。横線はコミットのつながり、Mは両方を統合した場合の例だ。

## 05｜② 目的｜機械学習でGitが重要になる理由

**このページの結論：** **実験結果の理由を追うには、実行時点のコードを特定する必要がある**。

### PART 01 — 役割を組み合わせる

1. **Git** — どのコードで実行したか
2. **MLflow** — どの条件・結果だったか
3. **分析** — 差異の理由を調べる
同じGitコミットから複数のRunを実行することもできる。

### PART 02 — 精度だけでは原因を追えない

ある実験のMAEが「274」、別の実験が「260」だったとする。数字だけでは、学習率の変更によるものか、特徴量の計算式の変更によるものか分からない。評価対象データが同一かも重要だ。

### PART 03 — GitコミットIDとMLflow Run ID

GitコミットIDはコードの履歴上の特定の状態を指し、Run IDは1回の実験実行を識別する。モデルの学習条件を変えて繰り返し実験する場合、Gitコミットは同じでもRun IDは毎回別になる。

## 06｜③ 概念・イメージ｜GitとGitHubは何が違う？

**このページの結論：** **GitはPC上で履歴を作るソフトウェア、GitHubはその履歴を共有するサービス**。

### PART 01 — コードと履歴の基本的な位置関係

1. **ローカルPC** — 編集・コミット
2. **push** — コミットを送信
3. **GitHub** — 共有・公開
GitHub PagesはGitHub上のWebファイルを公開する別の機能だ。

### PART 02 — 役割の違い

| 項目 | Git | GitHub |
| --- | --- | --- |
| 種類 | バージョン管理ソフトウェア | Gitを利用したホスティングサービス |
| 主な場所 | 自分のPC | インターネット上 |
| ネット接続 | 通常のコミットには不要 | 共有時には必要 |
| 主な用途 | 編集履歴とブランチ | 共有・レビュー・公開 |

### PART 03 — ローカルで履歴を作る

Gitでファイルの履歴を記録するには、GitHubアカウントは不要だ。PC内にGitが管理する情報を置いて、`git add`・`git commit`を実行できる。

### PART 04 — GitHubへ送るのは別の操作

ローカルでコミットしただけではGitHubの画面は更新されない。コミットをリモートリポジトリへ送る操作が `git push` だ。逆にGitHub側から変更を取り込む操作には `git fetch` や `git pull` がある。

## 07｜③ 概念・イメージ｜リポジトリと管理フォルダ

**このページの結論：** **リポジトリはプロジェクトの変更履歴を管理する単位**。Gitの内部情報は通常 `.git/` に保存する。

### PART 01 — PCのどこにファイルがある？

**図解（folders）：**

1. **my-project/** — Gitで管理するプロジェクトのフォルダ
2. **train.py** — 人が編集するPythonファイル
3. **.git/** — コミットやブランチの情報をGitが保持する隠しフォルダ
Gitの内部管理情報は通常、プロジェクト直下の .git フォルダに入る。

### PART 02 — リポジトリの範囲

DemandPilotというプロジェクトに `src/`、`tests/`、`README.md` がある場合、それらを1つの履歴として管理できる。個々のファイルごとではなく、プロジェクト全体の状態をコミットできる。

### PART 03 — ファイルとフォルダの例

```text
demandpilot/           【プロジェクトフォルダ】
├── .git/               【Gitの管理フォルダ】
├── src/                【ソースコードフォルダ】
│   └── train.py        【Pythonファイル】
├── tests/              【テストフォルダ】
│   └── test_train.py   【Pythonファイル】
└── README.md           【説明ファイル】
```
`.git/`が履歴・参照情報を格納する。プロジェクトの実ファイルは、これとは別の場所にある。

### PART 04 — `.git/`は何をしているのか

Gitはコミット履歴、ファイルの保存内容、ブランチの参照情報、ステージング情報などを `.git/` の内部に保存する。GitHubへ送るときも、それらから必要なGitオブジェクトや参照情報を送る。

### PART 05 — 注意

`.git` フォルダを手動で編集・削除すると、履歴情報が壊れたり失われたりする可能性がある。中身は通常Gitコマンドで操作する。

## 08｜③ 概念・イメージ｜3つの領域をイメージする

**このページの結論：** **編集・ステージング・コミットは別の段階**。`git add` と `git commit` の役割は異なる。

### PART 01 — ファイルが通る3つの管理領域

**図解（zones）：**

1. **作業ディレクトリ** — train.pyを編集する
2. **ステージングエリア** — git addで保存候補を選ぶ
3. **リポジトリ** — git commitで履歴を確定
実際にはファイルを単純に「移動」するのではなく、内容のスナップショットをインデックス・Gitオブジェクトへ記録する。

### PART 02 — Gitの3領域

1. **作業ディレクトリ** — 編集しているファイル
2. **ステージング** — 次に記録する内容
3. **Git履歴** — 確定したコミット
`git add`で内容をステージングへ登録、`git commit`でその内容をコミットとして確定する。

### PART 03 — 作業ディレクトリ

VS Codeなどで直接編集するファイルが置かれる場所だ。ここで `train.py` を直しても、それだけではGit履歴は変わらない。

### PART 04 — ステージングエリア

コミットに含める内容を準備する場所だ。正確にはGitが `.git/index` で管理する「次のコミットの候補」の状態だ。ファイルの追加・変更・削除のうち、どの状態を記録するか選ぶ。

### PART 05 — Git履歴（リポジトリ）

`git commit`で確定した結果はコミットとして記録される。後でコミットを指定して、その時点のファイル状態を確認・復元できる。

### PART 06 — 重要

ステージングは「ファイルを別の作業フォルダに移動する」という意味ではない。記録する内容のスナップショットを準備する処理だ。

### PART 07 — Gitの3領域を操作して確認する（疑似演習）

まず「編集する」を押し、次に「git add」「git commit」を押す。操作ごとに作業中の変更・ステージ済み内容・コミット数がどう変わるかを観察する。

> ブラウザ内シミュレーション。実際のGitコマンドは実行しない。

## 09｜③ 概念・イメージ｜コミットは「状態の記録」

**このページの結論：** **コミットは、ある時点の追跡ファイル全体の状態を指す記録**。過去の状態を後から復元できる。

### PART 01 — コミットは各時点の状態を参照できる

**図解（timeline）：**

1. **コミット A** — train.py: v1
2. **コミット B** — train.py: v2 + test.py
3. **コミット C** — train.py: v3 + test.py
変更された部分だけでなく、各時点の追跡ファイル全体を復元できる。

### PART 02 — コミットをセーブポイントとして考える

ゲームのセーブポイントのように「この時点では、どのファイルがどの内容だったか」を参照できる。後のコミットが追加されても、前のコミットを指す情報は通常残る。

### PART 03 — コミットごとのファイル内容（例）

| コミット | train.py | evaluate.py |
| --- | --- | --- |
| A | 平均値予測 | Accuracy計算 |
| B | LightGBM予測 | Accuracy計算 |
| C | LightGBM予測 | MAE計算 |

### PART 04 — 毎回ファイルを丸ごと複製するのか？

Gitは論理的には各コミットをファイル状態のスナップショットとして扱いる。一方、同じ内容のファイルはオブジェクトを再利用し、内部では圧縮や差分表現を利用することもある。各コミットごとにすべてのソースファイルを別名で複製する仕組みではない。

### PART 05 — ここが混同しやすい

コミットIDはモデルの学習条件を示すIDではない。コードと履歴の特定の状態を識別するものだ。

## 10｜③ 概念・イメージ｜ブランチとHEADのイメージ

**このページの結論：** **ブランチはコミットを指す名前付きの参照**。独立したフォルダのコピーではない。

### PART 01 — ブランチは別フォルダではなく参照

**図解（branch）：**

1. **main** — A → B
2. **feature** — B → C → D
featureはコミットDを指す名前。mainはコミットBを指す名前だ。

### PART 02 — 分岐している履歴のイメージ

```text
A --- B --- C   ← main
       \--- D   ← feature/model
            ↑
        HEAD（現在のブランチがfeatureの場合）
```
ブランチ名は最新のコミットを指し、新しいコミットを作るとその参照が進む。HEADは現在どこで作業しているかを示す。

### PART 03 — なぜ名前が動くのか

`feature/model`でDの次にEをコミットすると、feature/modelはDではなくEを指すようになる。一方、mainの参照はCのままだ。こうして、安定したmainを残しながら別の改善を試せる。

### PART 04 — HEADとは

通常HEADは「現在選択しているブランチ」を指す。例えば `git switch main`すると、HEADはmainを選び、作業ディレクトリもmainのコミットに合わせて切り替わる。ただし未コミット変更があると、衝突防止のため切り替えが拒否される場合がある。

## 11｜③ 概念・イメージ｜ローカルとリモートのリポジトリ

**このページの結論：** **ローカルとGitHubの履歴は別々**。共有するには明示的な同期操作が必要。

### PART 01 — ローカルとリモートの関係

1. **ローカルGit** — 編集・commit
2. **push** — GitHubへ送る
3. **リモートGit** — 共有される履歴
GitHubから取得した変更を取り込むときは逆方向にfetch/pullする。

### PART 02 — originとは

`origin`はリモートリポジトリの名前としてよく使われる既定の名前だ。GitHubの固有コマンドではない。`git remote -v` で登録先URLを確認できる。

### PART 03 — コミットしたのにWebサイトが更新されない理由

PCで `git commit`しただけではGitHubのmainには新しいコミットがない。公開サイトのコードもその時点では更新されない。ローカルで変更したコミットをGitHubへpushし、Pagesがデプロイして初めて公開が変わる。

### PART 04 — この段階のポイント

「Gitで履歴を保存する」と「GitHubに送る」は別だ。2つの操作を必ず区別する。

## 12｜④ 仕組み・構造｜`.git`フォルダの内部

**このページの結論：** **`.git/` 内のオブジェクトと参照情報が、Gitの履歴を成立させる**。

### PART 01 — 目に見えるコードとGitの管理領域

**図解（folders）：**

1. **project/** — プロジェクトのルート
2. **src/train.py** — 普段編集する学習コード
3. **.git/objects/** — 内容・ツリー・コミットをGit形式で保存
4. **.git/HEAD** — 現在のブランチ等を参照
 .git/ 配下はGitが管理するため、通常は手動で編集しない。

### PART 02 — 内部構成のイメージ

```text
.git/                     【フォルダ】
├── HEAD                   【テキストファイル】
├── index                  【バイナリファイル】
├── config                 【設定ファイル】
├── refs/                  【参照を管理するフォルダ】
│   └── heads/            【ローカルブランチへの参照】
└── objects/               【オブジェクト保存フォルダ】
    ├── xx/               【圧縮された個別オブジェクト】
    └── pack/             【まとめて圧縮したオブジェクト】
```
典型的な構成だ。Gitの最適化や参照保存方式によって、ファイルの有無は異なる。

### PART 03 — 内部データの役割

| 場所 | 何を保持するか |
| --- | --- |
| `.git/HEAD` | 現在のブランチやコミットを示す参照 |
| `.git/index` | ステージング中のファイルの状態 |
| `.git/objects/` | ファイル内容・ツリー・コミット等のGitオブジェクト |
| `.git/refs/heads/` | ブランチ名からコミットを参照する情報 |
| `.git/config` | このリポジトリ固有の設定 |

### PART 04 — ファイル名をそのまま保存するとは限らない

`train.py`をコミットした場合、Gitはファイルの内容をBlobオブジェクトとして保存する。元のファイル名やフォルダ構造との関係はTreeオブジェクトが保持する。したがって `.git/` に同名の `train.py` がそのまま置かれるとは限らない。

## 13｜④ 仕組み・構造｜追跡・未追跡・除外の仕組み

**このページの結論：** **Gitはファイルを追跡・未追跡・除外に分けて扱う**。新規ファイルは自動でコミットされない。

### PART 01 — ファイルごとに扱いが違う

**図解（compare）：**

1. **追跡する** — train.py・tests/・設定ファイル
2. **追跡しない** — 大容量データ・モデル・秘密の.env
 .gitignore は新規ファイルの除外判定に使われますが、追跡済みのファイルを自動解除しない。

### PART 02 — ファイルの状態

| 状態 | 意味 | 例 |
| --- | --- | --- |
| Tracked（追跡中） | Gitの管理対象として記録されたことがある | `src/train.py` |
| Untracked（未追跡） | 作業フォルダにあるがまだGitで追跡されていない | 新規作成した `memo.txt` |
| Ignored（除外） | 通常の追加候補から外す設定がある | `__pycache__/` や `.env` |

### PART 03 — `.gitignore`の役割

`.gitignore`は、通常の `git add` などで自動的に追加したくないパスを指定するテキストファイルだ。Pythonのキャッシュ、秘密情報、実験で生成された大きなファイルなどを除外するために使いる。

### PART 04 — `.gitignore` の例

```gitignore
.env
__pycache__/
.pytest_cache/
data/raw/
artifacts/
```
`.gitignore`自体はGitで管理できる。これは「未追跡ファイルの追加を避ける」ための設定だ。

### PART 05 — よくある誤解

すでに一度コミットして追跡中のファイルは、後から `.gitignore`に書いても追跡が解除されない。追跡をやめたい場合は `git rm --cached` など別の操作が必要だ。

## 14｜④ 仕組み・構造｜`git add`は何を保存するのか

**このページの結論：** **`git add` は実行時点のファイル内容をステージに登録する**。その後の再編集は別管理。

### PART 01 — addの前後を比較

**図解（zones）：**

1. **編集した train.py** — 作業フォルダの最新版
2. **git add train.py** — 現在の内容をステージに登録
3. **その後に再編集** — ステージには前回addした内容が残る
再編集分もコミットに含めたい場合は、もう一度 git add する。

### PART 02 — ステージされるのはaddした時点の内容

`train.py`を修正して `git add train.py`を実行すると、その時点でGitが確認したファイル内容がステージングへ登録される。その後さらにファイルを編集した場合、追加した変更は自動でステージングに反映されない。

### PART 03 — 同じファイルを2回編集した場合

| 時点 | 作業ディレクトリ | ステージング |
| --- | --- | --- |
| ① 初期状態 | 予測A | 予測A |
| ② 編集してadd | 予測B | 予測B |
| ③ さらに編集 | 予測C | 予測B |
| ④ commit | 予測C | 予測Bがコミットされる |

### PART 04 — なぜこの仕組みが役に立つのか

作業中の変更から「ここまでの修正だけを1コミットにしたい」と選べるためだ。同じファイルを後で追加編集した場合でも、いったん整理した変更を独立したコミットにできる。

### PART 05 — どう確認するか

`git diff`は主に作業ディレクトリとステージングの差、`git diff --staged`はステージングと直近のコミットの差を表示する。この2つを見ると、何がコミットされるのか区別できる。

## 15｜④ 仕組み・構造｜`git commit`の内部処理

**このページの結論：** **`git commit` はBlob・Tree・Commitを通じて、保存対象と過去の履歴を結び付ける**。

### PART 01 — コミットが参照する3種類のオブジェクト

**図解（objects）：**

1. **Blob** — ファイルの中身を保持
2. **Tree** — ファイル名・ディレクトリ構造を保持
3. **Commit** — Tree・親コミット・作成者・メッセージを参照
コードがそのまま「train.py」という名前で .git にコピーされるわけではない。

### PART 02 — 3種類のGitオブジェクト

1. **Blob** — ファイルの内容
2. **Tree** — 名前・フォルダの構成
3. **Commit** — Treeと履歴の情報
この3種類を組み合わせて、ある時点のコードの状態を表す。

### PART 03 — Blob：ファイルの中身

Blobオブジェクトにはファイル内容が保存される。Gitは内容をハッシュ化して識別する。内容が同じであれば、名前の違うファイルでも同じBlobを参照する場合がある。

### PART 04 — Tree：ファイル名や階層の対応

Treeオブジェクトには「この名前のファイルがどのBlobを参照するか」「このサブフォルダがどのTreeを参照するか」という関係が保存される。Gitのスナップショット全体の構造を表すものだ。

### PART 05 — Commit：いつ誰が、どの状態を確定したか

Commitオブジェクトには、参照するTree、親コミット、作成者・コミッター、時刻、コミットメッセージなどの情報が保存される。現在のブランチは新しいコミットを指すように更新される。

### PART 06 — コミットと内部情報の関係

```text
コミット C
  ├── Tree（当時のファイル一覧）
  │    ├── src/train.py → Blob #1
  │    └── README.md    → Blob #2
  └── 親コミット B
       └── 親コミット A
```
これは概念図だ。実際のGitは専用のオブジェクト形式を使い、Gitのハッシュ値を参照する。

### PART 07 — 全履歴を理解するための要点

どのコミットを指定すれば、どのTree・Blobへ到達するか追跡できる。これにより、過去時点のファイル内容を取り出せる。

## 16｜④ 仕組み・構造｜コミットするとブランチはどう動く？

**このページの結論：** **新しいコミットを作ると、現在のブランチが指す先が更新される**。

### PART 01 — HEADとブランチの関係

**図解（branch）：**

1. **HEAD** — 現在チェックアウトしているmainを指す
2. **main** — コミット Cを指す
3. **feature** — コミット Dを指す
コミットすると現在のブランチが新しいコミットを指すように動く。

### PART 02 — コミット前後の参照

```text
【コミット前】
A --- B ← main ← HEAD

【main上でCをコミット】
A --- B --- C ← main ← HEAD
```
HEADは通常「今選択しているブランチ」を通じて新しいコミットを指す。

### PART 03 — ブランチの正体は参照情報

mainブランチはフォルダ内に「main用のソースコード一式」を毎回コピーする仕組みではない。コミットを参照する名前として、Gitの内部情報に保持される。

### PART 04 — ブランチを切り替えるとどうなるか

`git switch feature/x`を実行すると、通常はHEADがそのブランチを指すようになる。同時に作業ディレクトリとステージングが、そのブランチのコミット内容に合わせて更新される。未コミット変更が破壊される可能性がある場合、Gitが切り替えを拒否することがある。

### PART 05 — Detached HEAD

コミットIDを直接チェックアウトした場合などには、HEADがブランチではなく特定コミットを直接指す状態もある。初学者はまず「通常はHEADが現在のブランチを指す」と覚える。

## 17｜④ 仕組み・構造｜マージの2つの形

**このページの結論：** **マージは別々に進んだ変更履歴を統合する操作**。履歴の状態により統合形式が変わる。

### PART 01 — 2つの開発履歴をまとめる

**図解（branch）：**

1. **main** — A → B → E
2. **feature** — B → C → D
3. **merge後** — E + D → M（統合）
条件によってはマージコミットを作らずfast-forwardすることもある。

### PART 02 — Fast-forward：mainだけが先に進んでいなかった場合

mainから分岐してfeatureでコミットし、その間mainが変化していなければ、mainの参照先をfeatureの先端まで進めるだけで統合できる場合がある。これをfast-forwardといいる。

### PART 03 — Fast-forwardのイメージ

```text
変更前: A --- B ← main
                 \--- C --- D ← feature

変更後: A --- B --- C --- D ← main, feature
```
mainがC・Dへ進むだけで、通常新しいマージコミットを作る必要はない。

### PART 04 — マージコミット：両方で開発が進んだ場合

mainでもfeatureでも新しいコミットが増えている場合、双方の変更を統合した新しいコミットを作ることがある。マージコミットは通常、2つの親コミットを持つ。

### PART 05 — マージコミットのイメージ

```text
A --- B --- C ---------- M ← main
       \                /
        D --- E --------  ← feature
```
CとEの両方の履歴を親として、Mで統合する。

### PART 06 — コンフリクトとは

同じ部分の変更が両立しない場合、Gitが自動で統合できず、どの内容を残すか人間の判断が必要だ。

## 18｜④ 仕組み・構造｜復元と取り消しの考え方

**このページの結論：** **確認・復元・取り消しは目的別にコマンドを使い分ける**。

### PART 01 — 「確認」「作業ファイルの復元」「取り消し」は別

**図解（compare）：**

1. **git show / diff** — 過去の内容を確認・比較
2. **git restore** — 作業ファイルを指定した状態に戻す
3. **git revert** — 変更を打ち消す新しいコミットを作る
操作前に対象ファイルと未コミット変更を確認する。

### PART 02 — どの範囲に影響する？

| 操作 | 主な用途 | 注意点 |
| --- | --- | --- |
| `git restore` | 作業ファイルやステージの内容を戻す | 未コミット変更が消える場合がある |
| `git revert` | 過去のコミットを打ち消す新しいコミットを作る | 通常は共有済み履歴に向く |
| `git reset` | HEADやステージの位置を変更する | オプション次第で履歴・作業内容を失う |

### PART 03 — 例：まだコミットしていない変更を取り消したい

`train.py`を編集しただけなら、`git restore train.py`でGitに記録済みの状態へ戻せる場合がある。ただし編集途中の未保存・未コミット変更は失われるため、内容を確認してから使いる。

### PART 04 — 例：push済みの不具合修正を打ち消したい

共有済みのコミットを「なかったこと」にするより、`git revert <commit>`で取り消し用の新しいコミットを作る方法が一般的だ。履歴を消さずに原因と対応を追跡できる。

### PART 05 — 最初は使わないもの

`git reset --hard`、`git push --force` などは作業内容や共有履歴を失う原因になる。必要性が明確でない限り、この講座では通常操作として推奨しない。

## 19｜⑤ 基本操作｜練習用リポジトリを作る

**このページの結論：** **`git init` で練習用フォルダをリポジトリに変える**。既存プロジェクトは触らない。

### PART 01 — Gitを始めるフォルダの例

**図解（folders）：**

1. **forecast-project/** — ここで git init を実行
2. **train.py** — 学習コード
3. **tests/test_train.py** — テストコード
4. **.git/** — 初期化後にできる履歴管理用フォルダ


### PART 02 — まずフォルダを分ける理由

すでにGitで管理しているリポジトリの中で `git init` を実行すると、意図しない状態になることがある。初学者は、自分で新しい空の練習用フォルダを作って試す方が安全だ。

### PART 03 — 空のGitリポジトリを作成

```bash
mkdir git-practice
cd git-practice
git init -b main
git status
```
`mkdir` はフォルダ作成、`cd` は移動、`git init -b main` はmainという名前の初期ブランチを使うGitリポジトリの初期化だ。

### PART 04 — 実行後の状態

作業フォルダに隠しフォルダ `.git/` が生成され、まだコミットがない空のリポジトリになる。`git status`では「main上にいてコミットがない」ことが確認できる。

### PART 05 — 表示例（環境で多少異なります）

```text
On branch main

No commits yet

nothing to commit (create/copy files and use "git add" to track)
```
これは実行結果の例であり、コマンドではない。

### PART 06 — 設定について

コミットで名前・メールの設定を求められた場合は `git config user.name "Learner"` と `git config user.email "learner@example.invalid"` を練習フォルダ内で設定できる。公開用ではGitHubのnoreplyメールを使う。

## 20｜⑤ 基本操作｜ファイルを作成した直後の状態

**このページの結論：** **新規ファイルは作成しただけでは未追跡**。まず `git status` で状態を確認する。

### PART 01 — 新しく作ったファイルはまだ未追跡

**図解（zones）：**

1. **新規作成** — train.py
2. **git status** — Untracked files と表示
3. **git add** — 追跡する内容としてステージ
ファイルを作っただけではGitは自動的にコミットしない。

### PART 02 — Pythonファイルを作る（Macのターミナル例）

```bash
cat > train.py <<'PY'
sales = [10, 20, 30, 40, 50, 60, 70]
prediction = sum(sales[-7:])
print(prediction)
PY

git status
```
`cat` の部分は新規ファイルを作るための例だ。VS Codeで同じtrain.pyを作っても構いない。

### PART 03 — 出力例

```text
Untracked files:
  train.py

nothing added to commit but untracked files present
```
Gitはtrain.pyの存在を把握していますが、まだ次のコミットに含める設定になっていない。

### PART 04 — なぜ自動で追跡されないのか

一時的なメモ、実験時に生成したログ、秘密情報まで無条件にコミット対象にしないためだ。Gitでは開発者が追加するファイルを選ぶ。

### PART 05 — この段階の確認

`git status`は「何が未追跡で、何が編集され、何がステージ済みか」を知るための最も基本的なコマンドだ。

## 21｜⑤ 基本操作｜`git add`で記録対象にする

**このページの結論：** **`git add` は「次のコミットに含める内容」を選ぶ操作**。まだ履歴は確定しない。

### PART 01 — 初めてのgit add

**図解（zones）：**

1. **作業** — train.pyにPythonを記述
2. **ステージ** — train.pyを登録
3. **Git履歴** — まだ新規コミットは存在しない
git addではまだコミットは作られない。

### PART 02 — ファイルをステージする

```bash
git add train.py
git status
```
指定したtrain.pyの内容がステージングに登録される。まだコミットは作られていない。

### PART 03 — 出力例

```text
Changes to be committed:
  new file:   train.py
```
「Changes to be committed」は次にコミットされる予定の内容だ。

### PART 04 — ここで何が変わった？

作業ディレクトリには引き続きtrain.pyが存在する。加えてGitのステージング（index）に、その時点のファイルの内容を参照する情報が登録されました。コミット履歴はまだ増えていない。

### PART 05 — 補足

`git add .`は現在のディレクトリ以下の変更をまとめて登録する。便利ですが、追加してはいけないファイルが紛れないよう、最初はファイル名を指定してaddすると理解しやすいだ。

## 22｜⑤ 基本操作｜`git commit`で履歴を確定する

**このページの結論：** **`git commit` で初めて保存時点が履歴として確定する**。`git log` で確認できる。

### PART 01 — 初回コミットの結果

**図解（timeline）：**

1. **git add** — 保存する対象を指定
2. **git commit** — コミット Aが作られる
3. **git log** — AのIDとメッセージを確認


### PART 02 — 最初のコミットを作る

```bash
git commit -m "最初の需要予測コードを追加"
git status
git log --oneline
```
`-m`の後ろはコミットメッセージだ。「なぜ・何を変更したか」が伝わる短い文章にする。

### PART 03 — 実行後の状態

`git log --oneline`には新しいコミットのIDとメッセージが表示される。作業内容がコミットと同じなら `git status`は「working tree clean」といった状態を示す。

### PART 04 — 表示例

```text
a1b2c3d (HEAD -> main) 最初の需要予測コードを追加
```
`a1b2c3d`は説明用の短縮IDだ。実際のIDは実行環境ごとに異なる。

### PART 05 — 忘れやすい点

この段階ではコミットがPC内に保存されただけだ。GitHubには自動送信されない。

## 23｜⑤ 基本操作｜編集内容を`git diff`で確認

**このページの結論：** **`git diff` は変更前後の行を比較する**。コミット前のレビューに使う。

### PART 01 — 変更点を把握してから記録

**図解（compare）：**

1. **変更前** — window = 7
2. **変更後** — window = 14
3. **git diff** — 変更前後の行を対比表示
まだステージしていない変更は通常 git diff で確認できる。

### PART 02 — train.pyを編集する例

```python
sales = [10, 20, 30, 40, 50, 60, 70]
prediction = sum(sales[-7:]) / 7
print(prediction)
```
さきほど作ったtrain.pyの2行目だけを、合計値から平均値の計算へ変更する例だ。

### PART 03 — 変更を確認

```bash
git status
git diff -- train.py
```
`git diff`はこの場面で、ステージングと作業ディレクトリの違いを表示する。

### PART 04 — 差分の表示例

```text
-prediction = sum(sales[-7:])
+prediction = sum(sales[-7:]) / 7
```
先頭が`-`の行は取り除く行、`+`の行は追加する行を表す。変更のない周辺行も表示されることがある。

### PART 05 — 差分を見る意味

「平均値に変更したつもりが、別のファイルも編集していた」などのミスをコミット前に発見できる。機械学習では特徴量や期間指定の細かな修正も精度に影響するため、差分確認が特に重要だ。

## 24｜⑤ 基本操作｜ステージ後の差分を読む

**このページの結論：** **`git diff` と `git diff --staged` は比較する領域が異なる**。

### PART 01 — 何と何を比較している？

**図解（zones）：**

1. **HEAD** — 最後のコミット
2. **ステージ** — 次にコミット予定の内容
3. **作業フォルダ** — 最後に編集した内容
git diff --staged はHEAD↔ステージ、git diffはステージ↔作業フォルダを比較する。

### PART 02 — ステージして2種類の差分を見る

```bash
git add train.py
git diff -- train.py
git diff --staged -- train.py
```
変更した後すぐaddしたなら、最初のdiffは空になり、`--staged`は合計から平均への差分を表示するはずだ。

### PART 03 — 2つの比較対象

`git diff`は作業中のファイルとステージングを比較する。一方 `git diff --staged`はステージングと直近コミットを比較する。つまり後者が「次にコミットする変更の候補」を確認するためのコマンドだ。

### PART 04 — もう一度編集するとどうなる？

```bash
git add train.py
# ここでVS Codeからtrain.pyをさらに変更する
git status
git diff
git diff --staged
```
新たな変更は作業側にだけ残り、以前の変更はステージ済みだ。再びgit addしない限り、最新の編集すべてがコミットに入るわけではない。

### PART 05 — 確認の習慣

コミット前に `git status` と `git diff --staged` を見る習慣を付けると、意図しないファイルや変更の混入に気づきやすくなる。

## 25｜⑤ 基本操作｜ステージングを取り消す

**このページの結論：** **ステージ解除と作業ファイルの破棄は別操作**。変更を消す前に対象を確認する。

### PART 01 — 2種類の「戻す」を混同しない

**図解（compare）：**

1. **git restore --staged** — ステージの変更を外す（作業ファイルは維持）
2. **git restore <file>** — 未コミットの作業ファイル変更を破棄する
後者は未保存の変更を失うことがあるため注意。

### PART 02 — ステージのみ解除する

```bash
git restore --staged train.py
git status
```
通常、作業ディレクトリのtrain.pyは変更されたまま残り、ステージングから外れる。

### PART 03 — 「保存対象の選択を解除」と考える

`git restore --staged`は次のコミット対象から戻す操作だ。作業ディレクトリでせっかく書いたコードを直ちに消すものではない。

### PART 04 — 作業ファイル自体を元に戻す操作

```bash
git restore -- train.py
```
こちらは作業ディレクトリの未ステージ変更を戻すため、未コミットの編集が消える可能性がある。実行前にdiffを確認する。

### PART 05 — 安全策

最初は `git status` → `git diff` / `git diff --staged` → 対象を指定したrestore、という順番で確認する。

## 26｜⑤ 基本操作｜過去のコミット内容を見る

**このページの結論：** **コミットIDを指定すると、過去の変更内容とファイルの状態を確認できる**。

### PART 01 — コミットIDから保存された内容にたどる

**図解（timeline）：**

1. **git log** — A / B / Cの履歴を一覧
2. **git show B** — コミットBの差分を確認
3. **git show B:path** — B時点のファイル内容を見る


### PART 02 — 直近の履歴と変更を確認

```bash
git log --oneline --max-count=5
git show --stat HEAD
git show HEAD:train.py
```
`HEAD`は現在参照中のコミットだ。`--stat`は変更ファイルの概要、`HEAD:train.py`はコミット内のファイル内容を表示する。

### PART 03 — 過去と現在の差を見る

コミットIDが分かれば、`git diff <古いID> HEAD -- train.py`でその時点と現在を比較できる。例えばモデルの予測ロジックを変えた場所を探すときに利用する。

### PART 04 — 2つのコミットを比較する例

```bash
git diff a1b2c3d HEAD -- train.py
```
`a1b2c3d`は説明用。実際は `git log --oneline` に表示されたコミットIDに置き換える。

### PART 05 — コミットIDの意味

コミットIDはバージョン番号のように通し番号で増えるのではなく、コミット内容等に基づくハッシュで生成される。

## 27｜⑤ 基本操作｜ブランチを作って切り替える

**このページの結論：** **`git switch -c` で改善用のブランチを作り、mainから分けて作業する**。

### PART 01 — 新ブランチはmainを保ったまま進む

**図解（branch）：**

1. **main** — コミット Bで待機
2. **feature/model** — BからC、Dへ開発
3. **git switch** — 現在の作業対象を切り替える


### PART 02 — 改善用のブランチを作る

```bash
git switch -c feature/mean-model
git branch
git status
```
`switch -c`はブランチを作成して、そのブランチに切り替える操作だ。`git branch`は一覧を表示し、現在のブランチには`*`が付く。

### PART 03 — 切り替え直後に何が変わるのか

作成した直後はmainと同じコミットを指す。ここから別のコードに変更してコミットすると、featureブランチだけが先に進み、mainは元のコミットを指したままになる。

### PART 04 — 切り替えと確認

```bash
git switch main
git log --oneline -3
git switch feature/mean-model
git log --oneline -3
```
作業ディレクトリの内容は、選択したブランチが指すコミットに合わせて切り替わる。

### PART 05 — 作業途中で切り替えられない場合

未コミット変更が切り替え先のファイルと衝突する場合、Gitは変更を守るため切り替えを拒否する。コミットするか、変更を退避してから切り替える。

## 28｜⑤ 基本操作｜ブランチを統合する

**このページの結論：** **確認済みの改善をmainへ統合するには `git merge` を使う**。

### PART 01 — merge前後の履歴イメージ

**図解（branch）：**

1. **main** — A → B
2. **feature** — B → C → D
3. **統合後** — A → B → C → D（fast-forward例）
変更状況によって統合方法は異なる。

### PART 02 — 統合の基本操作

```bash
git switch main
git merge feature/mean-model
git log --oneline --graph --all -6
```
`git merge`は「現在のブランチに、指定したブランチの変更を取り込む」操作だ。ここではmainへfeatureを取り込む。

### PART 03 — どんな結果になるのか

mainが分岐後に進んでいなければfast-forwardになることがある。mainでも別変更が進んでいればマージコミットが作られる場合がある。履歴は `git log --graph` で確認する。

### PART 04 — コンフリクトが起きたら

自動で統合できないファイルはGitが衝突を報告する。該当箇所を確認して正しいコードへ編集し、`git add <対象>`で解決済みにする。マージコミットを作る必要がある場合は `git commit` などで完了する。

### PART 05 — マージ前後のテスト

機械学習の前処理を変えた場合は、統合の前後でテストを実行する。コードとして整合していても、予測値が意図しない形に変わる可能性がある。

## 29｜⑤ 基本操作｜GitHubと共有する基本操作

**このページの結論：** **`commit` はローカル保存、`push` はGitHubへの送信**。操作対象を混同しない。

### PART 01 — ローカルとGitHubは別の保存場所

**図解（zones）：**

1. **ローカルGit** — commitして履歴を保存
2. **git push** — GitHubへコミットを送信
3. **GitHub** — 履歴が公開・共有される
pushしていないローカルコミットはGitHubに現れない。

### PART 02 — リモートの状態を確認

```bash
git remote -v
git branch -vv
```
リモートのURLとブランチの追跡設定を確認する。設定がないリポジトリでは何も表示されないことがある。

### PART 03 — GitHubの既存リポジトリを取得

```bash
git clone https://github.com/your-account/git-practice.git
```
`your-account`は自分のGitHubユーザー名に置き換える。実在するリポジトリURLが必要だ。

### PART 04 — コミットをGitHubに送る

```bash
git push -u origin main
```
`-u`は以降のpush/pullに利用する追跡先を設定する。リモートが未登録なら `git remote add origin <URL>` が必要だ。

### PART 05 — リモートの更新をローカルへ反映

```bash
git fetch origin
git pull --ff-only origin main
```
`fetch`はリモートの情報を取得、`pull`はローカルの現在ブランチへ取り込む。`--ff-only`は履歴をfast-forwardできる場合に限って実行する。

### PART 06 — 混乱しやすい点

`git pull`はGitHubに送るコマンドではなく、GitHubなどから更新を取り込むためのコマンドだ。

## 30｜⑤ 基本操作｜履歴を消さずに過去のコードを扱う

**このページの結論：** **過去の参照は `show`、ファイルの復元は `restore`、取り消し履歴は `revert`**。

### PART 01 — 目的ごとに安全なコマンドを選ぶ

**図解（compare）：**

1. **確認する** — git show / git diff
2. **ファイルを戻す** — git restore --source=ID
3. **共有履歴を打ち消す** — git revert


### PART 02 — 過去のコードを読む（変更しない）

```bash
git show a1b2c3d:train.py
git diff a1b2c3d HEAD -- train.py
```
この2つは表示・比較が目的だ。実行しても作業ディレクトリのファイルは基本的に書き換えない。

### PART 03 — 過去版を作業ファイルへ取り出す

```bash
git restore --source=a1b2c3d -- train.py
git status
```
実際のコミットIDに置き換える。作業ディレクトリのtrain.pyを過去版で置き換えるので、編集内容を失うおそれがある。

### PART 04 — 共有済みの不具合コミットを取り消す

```bash
git revert <取り消したいコミットID>
```
通常は取り消しのための新しいコミットを作る。衝突がある場合は手動の解決が必要だ。

### PART 05 — 初心者が避けたい操作

`reset --hard`や履歴のforce pushは、別の目的を持つ強い操作だ。今回は「見る」「作業ファイルへ取り出す」「新しいコミットで取り消す」を区別できれば十分だ。

## 31｜⑤ 基本操作｜Gitに入れないデータと秘密情報

**このページの結論：** **`.gitignore` は新たな追跡を避ける設定**。過去に保存した秘密情報は消えない。

### PART 01 — .gitignoreは過去を消さない

**図解（timeline）：**

1. **コミット前** — 機密ファイルを追跡しない
2. **コミット後** — .gitignore追加だけでは履歴に残る
3. **漏えい時** — 資格情報を失効・交換、履歴削除も検討


### PART 02 — 典型的な.gitignore

```gitignore
# 秘密情報
.env

# Pythonの一時ファイル
__pycache__/
.pytest_cache/

# 大容量データ・学習成果物
data/raw/
artifacts/
mlflow/
```
必要な設定ファイルやデータの保存方針はプロジェクトに合わせて調整する。

### PART 03 — 記録する必要がある情報とGit管理は別

学習データやモデルをGitから除外しても、実験の再現に必要な情報を管理しなくてよいわけではない。データの取得元、スナップショット、環境、MLflowのRunなどは別途記録する。

### PART 04 — すでに追跡していたファイルを追跡対象から外す

```bash
git rm --cached .env
git commit -m "認証情報ファイルの追跡を解除"
```
`.env`の実ファイルは作業フォルダに残しつつ、次のコミットからGitの追跡対象を外せる。ただし過去の履歴から秘密情報は消えない。

### PART 05 — 秘密情報が履歴に入った場合

GitHubへ公開してから `.env` を削除しただけでは、過去コミットに残る場合がある。該当の認証情報を無効化・再発行し、必要に応じて履歴の除去と公開状況の確認を行う必要がある。

## 32｜⑥ ユースケース｜DemandPilotで特徴量を追加する

**このページの結論：** **既存機能を守るため、変更は作業ブランチから始める**。

### PART 01 — 安全に進める標準的な流れ

1. **mainの状態を確認** — git status / log
2. **改善ブランチ** — switch -c
3. **編集・テスト** — diff / pytest
4. **変更を確定** — add / commit
検証・レビューが完了してからmainへ取り込む。

### PART 02 — 作業の前提

すでに `main` には動作確認済みのコードがあり、GitHubへ共有されているものとする。ここから新しい特徴量を追加し、モデルの精度を比較したい状況だ。

### PART 03 — 最初の確認と作業ブランチ

```bash
git status
git log --oneline -3
git switch -c feature/new-demand-feature
```
作業前に意図しない未コミット変更がないことを確認してからブランチを作る。

### PART 04 — DemandPilotの実行環境

DemandPilotのようにDockerでPythonを実行する構成なら、実際のテストもDockerコンテナ内で実行する。ここでのGitコマンド自体は通常ホストPCから操作する。

## 33｜⑥ ユースケース｜変更・テスト・コミットを一連で実行

**このページの結論：** **変更 → 差分確認 → テスト → コミット** の順に進めると、検証済みの変更を残せる。

### PART 01 — 開発と実験の境界

**図解（flow）：**

1. **編集** — features.pyを修正
2. **pytest** — 変更による不具合を検出
3. **git commit** — コードの状態を確定
4. **学習** — 確定したコードで実験


### PART 02 — コード変更とテストが1セット

例えば「販売数量の直近7日平均」を特徴量に加える場合、その計算式だけでなく、データリークを起こしていないか確認するテストも必要になる。コードと関連テストを同じ目的のコミットにまとめる。

### PART 03 — 実行手順の例（説明用）

```bash
# src/features.py を編集し、tests/test_features.py を更新
git status
git diff -- src/features.py tests/test_features.py

# Docker運用の場合のテスト例
docker compose run --rm --entrypoint pytest pipeline -q

# 変更内容をステージして確認
git add src/features.py tests/test_features.py
git diff --staged
git commit -m "需要予測の特徴量を追加"
```
上記のDockerコマンドはDemandPilotで使っているCompose構成を想定した例だ。テストの実行後にコミットする。

### PART 04 — なぜすぐcommitしないのか

動作確認前のコードも履歴に残せますが、機械学習では前処理や評価期間を誤ると数値だけが良く見える場合がある。少なくともテスト結果・意図しない差分の有無を確認してからコミットすると、履歴の意味が明確になる。

### PART 05 — 履歴から確認できること

このコミットには、特徴量の実装とテストの変更が含まれている。後日、評価の変化を調べる際に `git show <コミットID>` を使って「何を変えたか」を確認できる。

## 34｜⑥ ユースケース｜学習条件とコードのバージョンを記録

**このページの結論：** **1つのGitコミットから複数のMLflow Runを作成できる**。コードと実験は別の識別子で追跡する。

### PART 01 — 同じコードから複数の実験

**図解（flow）：**

1. **Git ID: A** — コードは同一
2. **Run 001** — 学習率0.1 → MAE 280
3. **Run 002** — 学習率0.01 → MAE 260
Git IDは同じでも、MLflowのRun IDは実験ごとに異なる。

### PART 02 — 学習前にコミットIDを確認

```bash
git status
git rev-parse HEAD
```
最初に `git status`で未コミット変更がないことを確認する。`git rev-parse HEAD`は現在参照しているコミットのIDを表示する。

### PART 03 — 実験とコードの対応（数値は架空）

| Gitコミット | MLflow Run | 学習率 | MAE |
| --- | --- | --- | --- |
| `f3a91bc` | Run 001 | 0.01 | 280 |
| `f3a91bc` | Run 002 | 0.001 | 260 |
| `f3a91bc` | Run 003 | 0.0001 | 267 |

### PART 04 — なぜGitコミットが同じでも良いのか

学習率は実行時のパラメータとして変えられるため、学習コードを変更しなければGitの履歴は増えない。一方MLflowのRunは実験のたびに別のIDを持ち、学習条件・精度・学習済みモデルなどを管理できる。

### PART 05 — Docker内でGitコミットIDを渡す例

```bash
# MacなどGitがある作業PC側
GIT_SHA=$(git rev-parse HEAD)
docker compose run --rm -e GIT_SHA="$GIT_SHA" pipeline train

# Pythonの学習処理側（考え方）
# mlflow.set_tag("git_commit", os.environ["GIT_SHA"])
```
この例はGitHub Pagesで動くものではなく、ローカルDocker/MLflowを組み合わせた運用例だ。Python側で明示的なタグ記録処理が必要だ。

### PART 06 — コンテナの場合の注意

Dockerイメージに `.git`を含めていない場合、学習プロセス内ではコミットIDを自動取得できないことがある。ホスト側でコミットIDを取得し、環境変数などでコンテナへ渡す方法がある。

## 35｜⑥ ユースケース｜精度が悪化した原因を追う

**このページの結論：** **精度悪化の調査は、コードの差分と学習条件の差分を切り分けることから始める**。

### PART 01 — 不具合・精度悪化時の調査

1. **MLflow** — Runの条件と評価
2. **Git** — Runに対応するコミット
3. **差分確認** — 変更内容を比較
データ期間、ライブラリ、乱数などの条件も合わせて確認する。

### PART 02 — 同じGitコミットの場合

同じコミットのRun間で精度が変わったなら、まず学習パラメータ、使用データ、データの分割、乱数シードなどを確認する。コードが同じでも、実行条件が違えば結果は変わる。

### PART 03 — 異なるGitコミットの場合

精度の差がある2つのRunに異なるコミットIDが記録されているなら、Gitでコードの差分を確認する。例えば特徴量のウィンドウ幅、対象期間、欠損値処理などが変更されていないか調べる。

### PART 04 — 2つのコードの違いを確認

```bash
git diff <以前のコミットID> <現在のコミットID> -- src/features.py
git show <現在のコミットID> --stat
```
`<...>`は説明用の置換箇所だ。実行時には実際のコミットIDを指定する。

## 36｜⑥ ユースケース｜GitHubへ公開・共有する

**このページの結論：** **共有するのはコミット済みの履歴**。`git push` の前に公開対象を確認する。

### PART 01 — 共同開発・共有の流れ

**図解（flow）：**

1. **ローカル** — 変更してコミット
2. **GitHub** — pushで共有
3. **ほかのPC** — fetch / pullで取得


### PART 02 — コミット済みの変更を確認

```bash
git status
git log --oneline -3
git remote -v
```
push先のURLが正しいことを確認する。別リポジトリへ誤って送信しないためにも重要だ。

### PART 03 — リモートへpushする

```bash
git push -u origin feature/new-demand-feature
```
改善ブランチをGitHubに送る例だ。mainへ統合する前にプルリクエストを作成してレビューする運用もある。

### PART 04 — GitHub Pagesの場合

Web教材のような静的サイトなら、GitHubの対象ブランチへHTML・CSS・JavaScriptなどをpushした後、GitHub Pagesのデプロイ処理によって公開ページへ反映される。単なるGit commitと、Webページの公開は異なる段階だ。

### PART 05 — 公開前に必ず見るもの

GitHubのPublicリポジトリは第三者がコードやコミット履歴を確認できる。秘密情報・社内ソース・個人情報・ライセンス条件に問題がないか、push前に確認する。

## 37｜⑦ まとめ｜全体を1枚で振り返る

**このページの結論：** **編集 → add → commit → push** が、変更をローカルの履歴から共有先へ届ける基本の流れ。

### PART 01 — 変更が履歴になるまで

1. **編集** — 作業ディレクトリ
2. **git add** — ステージング
3. **git commit** — ローカルの履歴
4. **git push** — GitHubへ共有
履歴を確認するときはlog/show/diff、別の作業を試すときはswitch/mergeを使いる。

### PART 02 — 何がしたい？→どのコマンド？

| やりたいこと | 主なコマンド |
| --- | --- |
| 現在の変更状態を知る | `git status` |
| 未ステージの差分を知る | `git diff` |
| 次のコミットに入れる | `git add` |
| 変更を履歴として残す | `git commit` |
| 履歴を一覧で見る | `git log` |
| 過去の中身を見る | `git show` |
| 別の改善を始める | `git switch -c` |
| 別のブランチを取り込む | `git merge` |
| 共有済みの修正を打ち消す | `git revert` |
| GitHubへコミットを送る | `git push` |

### PART 03 — Gitと他の技術の関係

Gitはコード履歴、Dockerは実行環境、pytestは動作確認、MLflowは実験とモデルの記録を主に担当する。機械学習の再現性を高めるには、これらを組み合わせて使う必要がある。

## 38｜⑦ まとめ｜現場で迷わないための確認事項

**このページの結論：** **コミット前・学習前・公開前の3つの確認が、安全な開発と再現性を支える**。

### PART 01 — Gitで再現性を支える情報の関係

**図解（compare）：**

1. **Gitコミット** — コード・実装状態
2. **データ・環境** — Git外も含めて管理
3. **MLflow Run** — 学習条件と結果を紐づけ


### PART 02 — コミット前

- `git status`で意図しないファイルがないか確認する
- `git diff`と`git diff --staged`で変更内容を読む
- 変更の目的が伝わるコミットメッセージを書く
- 必要なテストを実行し、結果を確認する

### PART 03 — モデル学習前

- 再現に使うコードがコミット済みであることを確認する
- GitコミットID・使用データ・分割方法・ライブラリ環境を特定できるようにする
- パラメータ・指標・モデルの保存先を決める

### PART 04 — GitHub公開前

- push先リポジトリとブランチを確認する
- 機密データ・個人情報・不要なモデルファイルがコミットに含まれていないことを確認する
- 公開後にWebサイトやREADMEのリンクが正常か確認する

## 知識問題（設問と回答）

### 問1　Gitでローカルのコミットを作ると、自動的にGitHubの公開サイトも更新される？

1. はい。commitするとすぐ更新される
2. いいえ。通常はpushなどが必要
3. ブランチを作れば必ず更新される

**正解：2**　git commitはローカルの履歴を作る操作だ。GitHubへ送るには通常git pushが必要だ。

### 問2　新しく作成したtrain.pyをGitの管理対象に入れる前の状態は？

1. 通常は未追跡（Untracked）
2. すでにコミット済み
3. 自動的にステージ済み

**正解：1**　新規ファイルはgit addするまで原則として未追跡だ。

### 問3　作業ディレクトリ・ステージング・コミットの順に相当する操作は？

1. commit → add → 編集
2. 編集 → add → commit
3. push → commit → add

**正解：2**　まずファイルを編集し、addで対象をステージして、commitで履歴に確定する。

### 問4　train.pyをaddした後、さらに編集した。次にcommitすると基本的にどの内容が入る？

1. addした時点の内容
2. 最後に編集した内容が必ずすべて入る
3. どちらも入らない

**正解：1**　addした時点でステージした内容が対象だ。後から編集した分は再度addしないと通常コミットに入らない。

### 問5　ステージ済み内容と直近のコミットの差分を見たいときは？

1. git diff --staged
2. git log --oneline
3. git push

**正解：1**　git diff --staged（--cachedも可）はステージングとHEADの差分を表示する。

### 問6　ある時点の追跡ファイル全体の構造を表すGitオブジェクトはどれ？

1. Blobだけ
2. Tree
3. HEADというソースコードファイル

**正解：2**　Blobは内容、Treeは名前とフォルダ構造との対応、CommitはTreeと履歴情報を保持する。

### 問7　Gitのブランチについて正しい説明は？

1. 必ずファイル一式を新しいフォルダに複製する
2. コミットを指す名前付きの参照である
3. GitHubでしか使えない

**正解：2**　ブランチはコミットを参照する情報だ。ローカルGitだけでも利用できる。

### 問8　HEADは通常何を示す？

1. 現在選択しているブランチ
2. 最も精度が良いモデル
3. 直近のMLflow Run ID

**正解：1**　通常HEADは現在選択中のブランチを示し、そこからコミットを参照する。

### 問9　すでに追跡中の.envを.gitignoreに追加すると、過去の履歴から秘密情報が消える？

1. はい。全履歴から消える
2. いいえ。追跡や履歴の除去には別対応が必要
3. GitHub Pagesだけから消える

**正解：2**　.gitignoreは未追跡ファイルの追加除外が中心だ。追跡済みファイルや過去履歴は消しない。

### 問10　未コミットの編集を残したまま、ステージだけ解除したいときは？

1. git restore --staged train.py
2. git reset --hard
3. git push

**正解：1**　git restore --stagedはステージ側の状態を戻し、通常は作業ファイルの変更を保持する。

### 問11　共有済みの不具合コミットを、履歴を消さずに打ち消したいときの代表的な操作は？

1. git revert
2. git init
3. git diff

**正解：1**　git revertは新しい取り消しコミットを作り、共有された履歴を保持する。

### 問12　mainが分岐以降に変わらず、featureだけ新しいコミットを積んだ。単純にmainへ取り込むと？

1. fast-forwardできる場合がある
2. 必ずコンフリクトする
3. リモートを必ず削除する

**正解：1**　mainの参照先をfeatureの先端に進めるだけで統合できる場合がある。

### 問13　同じGitコミットで学習率を変えて3回実験した場合、MLflowのRun IDは？

1. 同じコミットならRun IDも同じ
2. 3回の実験で別々のRun ID
3. Gitのブランチ名と等しい

**正解：2**　Gitコミットはコードの状態、MLflow Runは1回の実験を識別する。

### 問14　Dockerイメージから.gitを除外した場合、コンテナ内でGitコミットIDを自動取得できないことがある。対応例は？

1. ホスト側でコミットIDを取得して学習処理へ渡す
2. モデル重みをGitHubへ必ず登録する
3. GitHub Pagesを停止する

**正解：1**　ホストでgit rev-parse HEADを実行し、環境変数や実験タグを通じて学習プロセスに渡せる。

### 問15　精度の悪化を再現・分析するために、Gitコミットだけで十分？

1. 十分。Gitのコードだけで必ず再現できる
2. データ・依存環境・パラメータ等も必要
3. GitHubの星の数があれば十分

**正解：2**　コードが同じでもデータ、乱数、ライブラリ、学習条件などで結果は変わる。これらの追跡も必要だ。
