### 01. この講座でできるようになること

**このページの目標：** Gitの目的から操作・復元まで、学習後に説明・実行できる内容を把握する

Gitを初めて学ぶ人でも、最後には「何をどこに記録し、変更をどう戻すか」を理解できるように設計しています。コマンドの暗記だけを目的にしません。

#### ゴールは「操作の意味が分かる」こと
この講座の目標は、Pythonのコードを編集したときに、Gitがその変更をどう把握し、どの操作で履歴に保存するのか説明できることです。また、ブランチを使って改善を試し、問題があれば過去の状態を確認できるようになることを目指します。

#### 修了時にできること
- GitとGitHubの違いを説明できる

- status・diff・add・commit・logを目的に応じて使える
- ブランチの作成・切り替え・統合を説明できる
- 過去のコードを比較し、安全な方法で戻せる
- MLflowのRun IDとGitコミットIDの違いを説明できる

**補足／注意：学び方**

### 02. この講座で扱う範囲

**このページの目標：** Gitの基本範囲と、別講座に任せる範囲を区別できる

Gitは機械学習開発を支える複数の技術のうち「実装コードの履歴」を担当します。どこまでGitで管理するかも重要です。

#### 開発で使う技術の役割分担
| 対象 | 主な管理方法 | Gitだけで十分？ |
| --- | --- | --- |
| Pythonコード・テスト・設定ファイル | Git | はい（通常） |
| 学習条件・評価指標・保存モデル | MLflow | いいえ |
| 実行環境・OSライブラリ | Docker・依存関係固定 | いいえ |
| 大量の学習データ | データストレージ・DVC等 | 通常はいいえ |

#### なぜ役割を分けるのか
例えば学習済みモデルの重みは巨大になることがあります。コードと同じ方法でモデルのバイナリファイルを何度もGitに積むと、リポジトリが膨らみ、履歴管理も扱いづらくなります。Gitはコードの履歴に集中させ、実験結果はMLflowへ、環境はDockerへ分担させます。

**補足／注意：前提知識**
Pythonのファイルを作成・保存したことがあれば進められます。ターミナルの経験がなくても、コマンドの意味を1つずつ説明します。


## ② 目的

### 03. 上書き保存だけでは困る理由

**このページの目標：** Gitが必要になる具体的な問題を説明できる

昨日まで精度が良かった需要予測プログラムを今日改修したところ、精度が悪くなった場面を考えます。

#### 変更前に戻したくても、ファイルを上書きしている
`train.py`に特徴量を追加して保存すると、通常は新しい内容がファイルに残ります。前のコードを保存していなければ、「どの行を変えたか」「以前のコードはどうだったか」を簡単には確かめられません。

#### ファイル名にv1・v2を付ける方法の問題
`train_v1.py`、`train_final.py`、`train_final2.py`のように複製する方法では、どのファイルが正式版か分かりにくくなります。変更理由や、複数ファイルの組み合わせも記録しづらくなります。

#### Gitがある場合の考え方

最初の状態 → 改善 → 比較・復元

- **最初の状態：** 動くコードを記録
- **改善：** 新しいコードへ変更
- **比較・復元：** 過去と現在を追跡

Gitが記録するのは過去のファイル状態とその履歴です。モデルの精度そのものは自動で記録しません。

**補足／注意：この時点ではコマンドを覚えなくてよい**
「コードを変更したとき、以前の状態を安全に取り出せるようにしたい」という問題意識がGitを学ぶ出発点です。

### 04. 複数の作業を並行して進める理由

**このページの目標：** ブランチが必要になる状況を説明できる

予測モデルを改善しながら、既存のWeb画面の不具合も直したい場合を考えます。

#### すべて同じコードで作業すると混ざりやすい
「モデルの特徴量を追加する」変更と「画面を修正する」変更を同時に進めると、途中の不完全なコードが混ざることがあります。どちらか一方だけを取り込んだり、元に戻したりする作業も複雑になります。

#### ブランチで作業の流れを分ける
Gitでは、同じ履歴から新たな開発の流れを始められます。例えば `main` を動作確認済みの版として残し、`feature/add-feature` で新しい特徴量を試します。改善を確認した後にmainへ統合できます。

#### 作業の分岐イメージ
```text
A --- B ------------------- M   main
       \                 /
        C --- D ----------     feature/add-feature
```
A・B・C・D・Mは説明用のコミットです。横線はコミットのつながり、Mは両方を統合した場合の例です。

### 05. 機械学習でGitが重要になる理由

**このページの目標：** 機械学習の実験結果とコードの関係を説明できる

同じデータでも前処理やモデルの計算を変えれば予測精度は変化します。その結果の理由を調べるには、実験時点のコードを特定する必要があります。

#### 精度だけでは原因を追えない
ある実験のMAEが「274」、別の実験が「260」だったとします。数字だけでは、学習率の変更によるものか、特徴量の計算式の変更によるものか分かりません。評価対象データが同一かも重要です。

#### 役割を組み合わせる

Git → MLflow → 分析

- **Git：** どのコードで実行したか
- **MLflow：** どの条件・結果だったか
- **分析：** 差異の理由を調べる

同じGitコミットから複数のRunを実行することもできます。

#### GitコミットIDとMLflow Run ID
GitコミットIDはコードの履歴上の特定の状態を指し、Run IDは1回の実験実行を識別します。モデルの学習条件を変えて繰り返し実験する場合、Gitコミットは同じでもRun IDは毎回別になります。


## ③ 概念・イメージ

### 06. GitとGitHubは何が違う？

**このページの目標：** GitとGitHubを混同せず説明できる

GitはローカルPCでも利用できるソフトウェアです。GitHubはGitの履歴を保存・共有できるオンラインサービスです。

#### 役割の違い
| 項目 | Git | GitHub |
| --- | --- | --- |
| 種類 | バージョン管理ソフトウェア | Gitを利用したホスティングサービス |
| 主な場所 | 自分のPC | インターネット上 |
| ネット接続 | 通常のコミットには不要 | 共有時には必要 |
| 主な用途 | 編集履歴とブランチ | 共有・レビュー・公開 |

#### ローカルで履歴を作る
Gitでファイルの履歴を記録するには、GitHubアカウントは不要です。PC内にGitが管理する情報を置いて、`git add`・`git commit`を実行できます。

#### GitHubへ送るのは別の操作
ローカルでコミットしただけではGitHubの画面は更新されません。コミットをリモートリポジトリへ送る操作が `git push` です。逆にGitHub側から変更を取り込む操作には `git fetch` や `git pull` があります。

#### コードと履歴の基本的な位置関係

ローカルPC → push → GitHub

- **ローカルPC：** 編集・コミット
- **push：** コミットを送信
- **GitHub：** 共有・公開

GitHub PagesはGitHub上のWebファイルを公開する別の機能です。

### 07. リポジトリと管理フォルダ

**このページの目標：** リポジトリがどの範囲のファイルを管理するか説明できる

Gitを使う単位がリポジトリです。一般的には1つのプロジェクトフォルダを、1つのリポジトリとして扱います。

#### リポジトリの範囲
DemandPilotというプロジェクトに `src/`、`tests/`、`README.md` がある場合、それらを1つの履歴として管理できます。個々のファイルごとではなく、プロジェクト全体の状態をコミットできます。

#### ファイルとフォルダの例
```text
demandpilot/           【プロジェクトフォルダ】
├── .git/               【Gitの管理フォルダ】
├── src/                【ソースコードフォルダ】
│   └── train.py        【Pythonファイル】
├── tests/              【テストフォルダ】
│   └── test_train.py   【Pythonファイル】
└── README.md           【説明ファイル】
```
`.git/`が履歴・参照情報を格納します。プロジェクトの実ファイルは、これとは別の場所にあります。

#### `.git/`は何をしているのか
Gitはコミット履歴、ファイルの保存内容、ブランチの参照情報、ステージング情報などを `.git/` の内部に保存します。GitHubへ送るときも、それらから必要なGitオブジェクトや参照情報を送ります。

**補足／注意：注意**
`.git` フォルダを手動で編集・削除すると、履歴情報が壊れたり失われたりする可能性があります。中身は通常Gitコマンドで操作します。

### 08. 3つの領域をイメージする

**このページの目標：** 作業・ステージング・履歴の3領域を区別できる

Gitはファイルを編集しただけでは履歴を確定しません。変更を確定する前に、一時的に「次のコミットに入れる内容」を選べる仕組みがあります。

#### Gitの3領域

作業ディレクトリ → ステージング → Git履歴

- **作業ディレクトリ：** 編集しているファイル
- **ステージング：** 次に記録する内容
- **Git履歴：** 確定したコミット

`git add`で内容をステージングへ登録、`git commit`でその内容をコミットとして確定します。

#### 作業ディレクトリ
VS Codeなどで直接編集するファイルが置かれる場所です。ここで `train.py` を直しても、それだけではGit履歴は変わりません。

#### ステージングエリア
コミットに含める内容を準備する場所です。正確にはGitが `.git/index` で管理する「次のコミットの候補」の状態です。ファイルの追加・変更・削除のうち、どの状態を記録するか選びます。

#### Git履歴（リポジトリ）
`git commit`で確定した結果はコミットとして記録されます。後でコミットを指定して、その時点のファイル状態を確認・復元できます。

**補足／注意：重要**
ステージングは「ファイルを別の作業フォルダに移動する」という意味ではありません。記録する内容のスナップショットを準備する処理です。

#### 疑似操作：Gitの3領域を操作して確認する（疑似演習）
まず「編集する」を押し、次に「git add」「git commit」を押します。操作ごとに作業中の変更・ステージ済み内容・コミット数がどう変わるかを観察してください。

### 09. コミットは「状態の記録」

**このページの目標：** コミットが差分だけでなくプロジェクトの状態を表すことを説明できる

コミットとは、その時点で追跡対象になっているファイルの状態を示す保存記録です。

#### コミットをセーブポイントとして考える
ゲームのセーブポイントのように「この時点では、どのファイルがどの内容だったか」を参照できます。後のコミットが追加されても、前のコミットを指す情報は通常残ります。

#### コミットごとのファイル内容（例）
| コミット | train.py | evaluate.py |
| --- | --- | --- |
| A | 平均値予測 | Accuracy計算 |
| B | LightGBM予測 | Accuracy計算 |
| C | LightGBM予測 | MAE計算 |

#### 毎回ファイルを丸ごと複製するのか？
Gitは論理的には各コミットをファイル状態のスナップショットとして扱います。一方、同じ内容のファイルはオブジェクトを再利用し、内部では圧縮や差分表現を利用することもあります。各コミットごとにすべてのソースファイルを別名で複製する仕組みではありません。

**補足／注意：ここが混同しやすい**
コミットIDはモデルの学習条件を示すIDではありません。コードと履歴の特定の状態を識別するものです。

### 10. ブランチとHEADのイメージ

**このページの目標：** ブランチとHEADが何を指すか説明できる

ブランチは「別フォルダ」でも「履歴全体のコピー」でもなく、コミットを指す名前付きの参照です。

#### 分岐している履歴のイメージ
```text
A --- B --- C   ← main
       \--- D   ← feature/model
            ↑
        HEAD（現在のブランチがfeatureの場合）
```
ブランチ名は最新のコミットを指し、新しいコミットを作るとその参照が進みます。HEADは現在どこで作業しているかを示します。

#### なぜ名前が動くのか
`feature/model`でDの次にEをコミットすると、feature/modelはDではなくEを指すようになります。一方、mainの参照はCのままです。こうして、安定したmainを残しながら別の改善を試せます。

#### HEADとは
通常HEADは「現在選択しているブランチ」を指します。例えば `git switch main`すると、HEADはmainを選び、作業ディレクトリもmainのコミットに合わせて切り替わります。ただし未コミット変更があると、衝突防止のため切り替えが拒否される場合があります。

### 11. ローカルとリモートのリポジトリ

**このページの目標：** ローカルのコミットとGitHub上のコミットの違いを説明できる

Gitの履歴は、自分のPCとGitHubに別々に存在します。同期は明示的な操作で行います。

#### ローカルとリモートの関係

ローカルGit → push → リモートGit

- **ローカルGit：** 編集・commit
- **push：** GitHubへ送る
- **リモートGit：** 共有される履歴

GitHubから取得した変更を取り込むときは逆方向にfetch/pullします。

#### originとは
`origin`はリモートリポジトリの名前としてよく使われる既定の名前です。GitHubの固有コマンドではありません。`git remote -v` で登録先URLを確認できます。

#### コミットしたのにWebサイトが更新されない理由
PCで `git commit`しただけではGitHubのmainには新しいコミットがありません。公開サイトのコードもその時点では更新されません。ローカルで変更したコミットをGitHubへpushし、Pagesがデプロイして初めて公開が変わります。

**補足／注意：この段階のポイント**
「Gitで履歴を保存する」と「GitHubに送る」は別です。2つの操作を必ず区別してください。


## ④ 仕組み・構造

### 12. `.git`フォルダの内部

**このページの目標：** Gitの主な管理ファイル・フォルダの保存先を理解する

Gitは「見えないところで勝手に履歴を管理する魔法」ではありません。履歴を管理するための情報を `.git/` に実際に記録しています。

#### 内部構成のイメージ
```text
.git/                     【フォルダ】
├── HEAD                   【テキストファイル】
├── index                  【バイナリファイル】
├── config                 【設定ファイル】
├── refs/                  【参照を管理するフォルダ】
│   └── heads/            【ローカルブランチへの参照】
└── objects/               【オブジェクト保存フォルダ】
    ├── xx/               【圧縮された個別オブジェクト】
    └── pack/             【まとめて圧縮したオブジェクト】
```
典型的な構成です。Gitの最適化や参照保存方式によって、ファイルの有無は異なります。

#### 内部データの役割
| 場所 | 何を保持するか |
| --- | --- |
| `.git/HEAD` | 現在のブランチやコミットを示す参照 |
| `.git/index` | ステージング中のファイルの状態 |
| `.git/objects/` | ファイル内容・ツリー・コミット等のGitオブジェクト |
| `.git/refs/heads/` | ブランチ名からコミットを参照する情報 |
| `.git/config` | このリポジトリ固有の設定 |

#### ファイル名をそのまま保存するとは限らない
`train.py`をコミットした場合、Gitはファイルの内容をBlobオブジェクトとして保存します。元のファイル名やフォルダ構造との関係はTreeオブジェクトが保持します。したがって `.git/` に同名の `train.py` がそのまま置かれるとは限りません。

### 13. 追跡・未追跡・除外の仕組み

**このページの目標：** tracked / untracked / ignoredの区別を説明できる

Gitはフォルダに存在するすべてのファイルを、無条件にコミットするわけではありません。

#### ファイルの状態
| 状態 | 意味 | 例 |
| --- | --- | --- |
| Tracked（追跡中） | Gitの管理対象として記録されたことがある | `src/train.py` |
| Untracked（未追跡） | 作業フォルダにあるがまだGitで追跡されていない | 新規作成した `memo.txt` |
| Ignored（除外） | 通常の追加候補から外す設定がある | `__pycache__/` や `.env` |

#### `.gitignore`の役割
`.gitignore`は、通常の `git add` などで自動的に追加したくないパスを指定するテキストファイルです。Pythonのキャッシュ、秘密情報、実験で生成された大きなファイルなどを除外するために使います。

#### `.gitignore` の例
```gitignore
.env
__pycache__/
.pytest_cache/
data/raw/
artifacts/
```
`.gitignore`自体はGitで管理できます。これは「未追跡ファイルの追加を避ける」ための設定です。

**補足／注意：よくある誤解**
すでに一度コミットして追跡中のファイルは、後から `.gitignore`に書いても追跡が解除されません。追跡をやめたい場合は `git rm --cached` など別の操作が必要です。

### 14. `git add`は何を保存するのか

**このページの目標：** git addが実行時点のファイル内容をステージすることを説明できる

ステージングは、コミットしたい内容を選んで準備する工程です。重要なのは「いつの内容が記録されるのか」です。

#### ステージされるのはaddした時点の内容
`train.py`を修正して `git add train.py`を実行すると、その時点でGitが確認したファイル内容がステージングへ登録されます。その後さらにファイルを編集した場合、追加した変更は自動でステージングに反映されません。

#### 同じファイルを2回編集した場合
| 時点 | 作業ディレクトリ | ステージング |
| --- | --- | --- |
| ① 初期状態 | 予測A | 予測A |
| ② 編集してadd | 予測B | 予測B |
| ③ さらに編集 | 予測C | 予測B |
| ④ commit | 予測C | 予測Bがコミットされる |

#### なぜこの仕組みが役に立つのか
作業中の変更から「ここまでの修正だけを1コミットにしたい」と選べるためです。同じファイルを後で追加編集した場合でも、いったん整理した変更を独立したコミットにできます。

**補足／注意：どう確認するか**
`git diff`は主に作業ディレクトリとステージングの差、`git diff --staged`はステージングと直近のコミットの差を表示します。この2つを見ると、何がコミットされるのか区別できます。

### 15. `git commit`の内部処理

**このページの目標：** Blob・Tree・Commitオブジェクトの役割と履歴のつながりを説明できる

`git commit`は単に変更ファイルをコピーする処理ではありません。ステージングの状態から、後で参照できるコミットを作ります。

#### 3種類のGitオブジェクト

Blob → Tree → Commit

- **Blob：** ファイルの内容
- **Tree：** 名前・フォルダの構成
- **Commit：** Treeと履歴の情報

この3種類を組み合わせて、ある時点のコードの状態を表します。

#### Blob：ファイルの中身
Blobオブジェクトにはファイル内容が保存されます。Gitは内容をハッシュ化して識別します。内容が同じであれば、名前の違うファイルでも同じBlobを参照する場合があります。

#### Tree：ファイル名や階層の対応
Treeオブジェクトには「この名前のファイルがどのBlobを参照するか」「このサブフォルダがどのTreeを参照するか」という関係が保存されます。Gitのスナップショット全体の構造を表すものです。

#### Commit：いつ誰が、どの状態を確定したか
Commitオブジェクトには、参照するTree、親コミット、作成者・コミッター、時刻、コミットメッセージなどの情報が保存されます。現在のブランチは新しいコミットを指すように更新されます。

#### コミットと内部情報の関係
```text
コミット C
  ├── Tree（当時のファイル一覧）
  │    ├── src/train.py → Blob #1
  │    └── README.md    → Blob #2
  └── 親コミット B
       └── 親コミット A
```
これは概念図です。実際のGitは専用のオブジェクト形式を使い、Gitのハッシュ値を参照します。

**補足／注意：全履歴を理解するための要点**
どのコミットを指定すれば、どのTree・Blobへ到達するか追跡できます。これにより、過去時点のファイル内容を取り出せます。

### 16. コミットするとブランチはどう動く？

**このページの目標：** HEAD・ブランチ参照・コミットの更新関係を説明できる

コミットを作ったときに更新されるのは、通常、現在のブランチが指す先です。

#### コミット前後の参照
```text
【コミット前】
A --- B ← main ← HEAD

【main上でCをコミット】
A --- B --- C ← main ← HEAD
```
HEADは通常「今選択しているブランチ」を通じて新しいコミットを指します。

#### ブランチの正体は参照情報
mainブランチはフォルダ内に「main用のソースコード一式」を毎回コピーする仕組みではありません。コミットを参照する名前として、Gitの内部情報に保持されます。

#### ブランチを切り替えるとどうなるか
`git switch feature/x`を実行すると、通常はHEADがそのブランチを指すようになります。同時に作業ディレクトリとステージングが、そのブランチのコミット内容に合わせて更新されます。未コミット変更が破壊される可能性がある場合、Gitが切り替えを拒否することがあります。

**補足／注意：Detached HEAD**
コミットIDを直接チェックアウトした場合などには、HEADがブランチではなく特定コミットを直接指す状態もあります。初学者はまず「通常はHEADが現在のブランチを指す」と覚えましょう。

### 17. マージの2つの形

**このページの目標：** fast-forwardとマージコミットの違いを説明できる

マージは変更の履歴を統合する操作ですが、状況によって履歴の形が変わります。

#### Fast-forward：mainだけが先に進んでいなかった場合
mainから分岐してfeatureでコミットし、その間mainが変化していなければ、mainの参照先をfeatureの先端まで進めるだけで統合できる場合があります。これをfast-forwardといいます。

#### Fast-forwardのイメージ
```text
変更前: A --- B ← main
                 \--- C --- D ← feature

変更後: A --- B --- C --- D ← main, feature
```
mainがC・Dへ進むだけで、通常新しいマージコミットを作る必要はありません。

#### マージコミット：両方で開発が進んだ場合
mainでもfeatureでも新しいコミットが増えている場合、双方の変更を統合した新しいコミットを作ることがあります。マージコミットは通常、2つの親コミットを持ちます。

#### マージコミットのイメージ
```text
A --- B --- C ---------- M ← main
       \                /
        D --- E --------  ← feature
```
CとEの両方の履歴を親として、Mで統合します。

**補足／注意：コンフリクトとは**
同じ部分の変更が両立しない場合、Gitが自動で統合できず、どの内容を残すか人間の判断が必要です。

### 18. 復元と取り消しの考え方

**このページの目標：** restore・revert・resetを安全性の観点で区別できる

Gitには「元に戻す」操作が複数ありますが、何を戻すかが異なります。コマンド名だけで判断しないようにします。

#### どの範囲に影響する？
| 操作 | 主な用途 | 注意点 |
| --- | --- | --- |
| `git restore` | 作業ファイルやステージの内容を戻す | 未コミット変更が消える場合がある |
| `git revert` | 過去のコミットを打ち消す新しいコミットを作る | 通常は共有済み履歴に向く |
| `git reset` | HEADやステージの位置を変更する | オプション次第で履歴・作業内容を失う |

#### 例：まだコミットしていない変更を取り消したい
`train.py`を編集しただけなら、`git restore train.py`でGitに記録済みの状態へ戻せる場合があります。ただし編集途中の未保存・未コミット変更は失われるため、内容を確認してから使います。

#### 例：push済みの不具合修正を打ち消したい
共有済みのコミットを「なかったこと」にするより、`git revert <commit>`で取り消し用の新しいコミットを作る方法が一般的です。履歴を消さずに原因と対応を追跡できます。

**補足／注意：最初は使わないもの**
`git reset --hard`、`git push --force` などは作業内容や共有履歴を失う原因になります。必要性が明確でない限り、この講座では通常操作として推奨しません。

### 19. 練習用リポジトリを作る

**このページの目標：** 安全な練習フォルダを作りGit管理を開始できる

ここからはMacのターミナルで実際に実行できる例です。既存のDemandPilotを壊さないよう、独立した練習用フォルダで作業します。

#### まずフォルダを分ける理由
すでにGitで管理しているリポジトリの中で `git init` を実行すると、意図しない状態になることがあります。初学者は、自分で新しい空の練習用フォルダを作って試す方が安全です。

#### 空のGitリポジトリを作成
```bash
mkdir git-practice
cd git-practice
git init -b main
git status
```
`mkdir` はフォルダ作成、`cd` は移動、`git init -b main` はmainという名前の初期ブランチを使うGitリポジトリの初期化です。

#### 実行後の状態
作業フォルダに隠しフォルダ `.git/` が生成され、まだコミットがない空のリポジトリになります。`git status`では「main上にいてコミットがない」ことが確認できます。

#### 表示例（環境で多少異なります）
```text
On branch main

No commits yet

nothing to commit (create/copy files and use "git add" to track)
```
これは実行結果の例であり、コマンドではありません。

**補足／注意：設定について**
コミットで名前・メールの設定を求められた場合は `git config user.name "Learner"` と `git config user.email "learner@example.invalid"` を練習フォルダ内で設定できます。公開用ではGitHubのnoreplyメールを使ってください。

### 20. ファイルを作成した直後の状態

**このページの目標：** 新しいファイルがuntrackedになることとstatusの表示を理解する

Gitは新しいファイルを作っただけでは追跡しません。まず状態を確認します。

#### Pythonファイルを作る（Macのターミナル例）
```bash
cat > train.py <<'PY'
sales = [10, 20, 30, 40, 50, 60, 70]
prediction = sum(sales[-7:])
print(prediction)
PY

git status
```
`cat` の部分は新規ファイルを作るための例です。VS Codeで同じtrain.pyを作っても構いません。

#### 出力例
```text
Untracked files:
  train.py

nothing added to commit but untracked files present
```
Gitはtrain.pyの存在を把握していますが、まだ次のコミットに含める設定になっていません。

#### なぜ自動で追跡されないのか
一時的なメモ、実験時に生成したログ、秘密情報まで無条件にコミット対象にしないためです。Gitでは開発者が追加するファイルを選びます。

**補足／注意：この段階の確認**
`git status`は「何が未追跡で、何が編集され、何がステージ済みか」を知るための最も基本的なコマンドです。

### 21. `git add`で記録対象にする

**このページの目標：** 未追跡のファイルをステージングに追加し状態を確認できる

次のコミットへ含めるファイルを選択します。

#### ファイルをステージする
```bash
git add train.py
git status
```
指定したtrain.pyの内容がステージングに登録されます。まだコミットは作られていません。

#### 出力例
```text
Changes to be committed:
  new file:   train.py
```
「Changes to be committed」は次にコミットされる予定の内容です。

#### ここで何が変わった？
作業ディレクトリには引き続きtrain.pyが存在します。加えてGitのステージング（index）に、その時点のファイルの内容を参照する情報が登録されました。コミット履歴はまだ増えていません。

**補足／注意：補足**
`git add .`は現在のディレクトリ以下の変更をまとめて登録します。便利ですが、追加してはいけないファイルが紛れないよう、最初はファイル名を指定してaddすると理解しやすいです。

### 22. `git commit`で履歴を確定する

**このページの目標：** 初回コミットを作成し、commitとpushを区別できる

ステージングに登録した内容から、最初のコミットを作ります。

#### 最初のコミットを作る
```bash
git commit -m "最初の需要予測コードを追加"
git status
git log --oneline
```
`-m`の後ろはコミットメッセージです。「なぜ・何を変更したか」が伝わる短い文章にします。

#### 実行後の状態
`git log --oneline`には新しいコミットのIDとメッセージが表示されます。作業内容がコミットと同じなら `git status`は「working tree clean」といった状態を示します。

#### 表示例
```text
a1b2c3d (HEAD -> main) 最初の需要予測コードを追加
```
`a1b2c3d`は説明用の短縮IDです。実際のIDは実行環境ごとに異なります。

**補足／注意：忘れやすい点**
この段階ではコミットがPC内に保存されただけです。GitHubには自動送信されません。

### 23. 編集内容を`git diff`で確認

**このページの目標：** 差分表示の + と - の意味を読み取れる

既存ファイルを修正したとき、何が変わったか確認します。

#### train.pyを編集する例
```python
sales = [10, 20, 30, 40, 50, 60, 70]
prediction = sum(sales[-7:]) / 7
print(prediction)
```
さきほど作ったtrain.pyの2行目だけを、合計値から平均値の計算へ変更する例です。

#### 変更を確認
```bash
git status
git diff -- train.py
```
`git diff`はこの場面で、ステージングと作業ディレクトリの違いを表示します。

#### 差分の表示例
```text
-prediction = sum(sales[-7:])
+prediction = sum(sales[-7:]) / 7
```
先頭が`-`の行は取り除く行、`+`の行は追加する行を表します。変更のない周辺行も表示されることがあります。

#### 差分を見る意味
「平均値に変更したつもりが、別のファイルも編集していた」などのミスをコミット前に発見できます。機械学習では特徴量や期間指定の細かな修正も精度に影響するため、差分確認が特に重要です。

### 24. ステージ後の差分を読む

**このページの目標：** git diffとgit diff --stagedを区別できる

変更をaddした後、実際にコミットされる内容を確認します。

#### ステージして2種類の差分を見る
```bash
git add train.py
git diff -- train.py
git diff --staged -- train.py
```
変更した後すぐaddしたなら、最初のdiffは空になり、`--staged`は合計から平均への差分を表示するはずです。

#### 2つの比較対象
`git diff`は作業中のファイルとステージングを比較します。一方 `git diff --staged`はステージングと直近コミットを比較します。つまり後者が「次にコミットする変更の候補」を確認するためのコマンドです。

#### もう一度編集するとどうなる？
```bash
git add train.py
# ここでVS Codeからtrain.pyをさらに変更する
git status
git diff
git diff --staged
```
新たな変更は作業側にだけ残り、以前の変更はステージ済みです。再びgit addしない限り、最新の編集すべてがコミットに入るわけではありません。

**補足／注意：確認の習慣**
コミット前に `git status` と `git diff --staged` を見る習慣を付けると、意図しないファイルや変更の混入に気づきやすくなります。

### 25. ステージングを取り消す

**このページの目標：** ステージ取り消しとファイル編集の取り消しを区別できる

間違えて `git add`したとき、作業中のファイルを消さずにステージだけ解除できます。

#### ステージのみ解除する
```bash
git restore --staged train.py
git status
```
通常、作業ディレクトリのtrain.pyは変更されたまま残り、ステージングから外れます。

#### 「保存対象の選択を解除」と考える
`git restore --staged`は次のコミット対象から戻す操作です。作業ディレクトリでせっかく書いたコードを直ちに消すものではありません。

#### 作業ファイル自体を元に戻す操作
```bash
git restore -- train.py
```
こちらは作業ディレクトリの未ステージ変更を戻すため、未コミットの編集が消える可能性があります。実行前にdiffを確認してください。

**補足／注意：安全策**
最初は `git status` → `git diff` / `git diff --staged` → 対象を指定したrestore、という順番で確認しましょう。

### 26. 過去のコミット内容を見る

**このページの目標：** log・show・diffを使って変更内容を確認できる

履歴を残すメリットは、後から内容を確認できる点にあります。

#### 直近の履歴と変更を確認
```bash
git log --oneline --max-count=5
git show --stat HEAD
git show HEAD:train.py
```
`HEAD`は現在参照中のコミットです。`--stat`は変更ファイルの概要、`HEAD:train.py`はコミット内のファイル内容を表示します。

#### 過去と現在の差を見る
コミットIDが分かれば、`git diff <古いID> HEAD -- train.py`でその時点と現在を比較できます。例えばモデルの予測ロジックを変えた場所を探すときに利用します。

#### 2つのコミットを比較する例
```bash
git diff a1b2c3d HEAD -- train.py
```
`a1b2c3d`は説明用。実際は `git log --oneline` に表示されたコミットIDに置き換えます。

**補足／注意：コミットIDの意味**
コミットIDはバージョン番号のように通し番号で増えるのではなく、コミット内容等に基づくハッシュで生成されます。

### 27. ブランチを作って切り替える

**このページの目標：** switch・branchコマンドで独立した変更を管理できる

動いているコードをmainに残しながら、新しい予測方法を試す例です。

#### 改善用のブランチを作る
```bash
git switch -c feature/mean-model
git branch
git status
```
`switch -c`はブランチを作成して、そのブランチに切り替える操作です。`git branch`は一覧を表示し、現在のブランチには`*`が付きます。

#### 切り替え直後に何が変わるのか
作成した直後はmainと同じコミットを指します。ここから別のコードに変更してコミットすると、featureブランチだけが先に進み、mainは元のコミットを指したままになります。

#### 切り替えと確認
```bash
git switch main
git log --oneline -3
git switch feature/mean-model
git log --oneline -3
```
作業ディレクトリの内容は、選択したブランチが指すコミットに合わせて切り替わります。

**補足／注意：作業途中で切り替えられない場合**
未コミット変更が切り替え先のファイルと衝突する場合、Gitは変更を守るため切り替えを拒否します。コミットするか、変更を退避してから切り替えます。

### 28. ブランチを統合する

**このページの目標：** mergeを実行する順番と結果を説明できる

feature側の改修が動作確認できたら、安定版として使うmainに取り込みます。

#### 統合の基本操作
```bash
git switch main
git merge feature/mean-model
git log --oneline --graph --all -6
```
`git merge`は「現在のブランチに、指定したブランチの変更を取り込む」操作です。ここではmainへfeatureを取り込みます。

#### どんな結果になるのか
mainが分岐後に進んでいなければfast-forwardになることがあります。mainでも別変更が進んでいればマージコミットが作られる場合があります。履歴は `git log --graph` で確認します。

#### コンフリクトが起きたら
自動で統合できないファイルはGitが衝突を報告します。該当箇所を確認して正しいコードへ編集し、`git add <対象>`で解決済みにします。マージコミットを作る必要がある場合は `git commit` などで完了します。

**補足／注意：マージ前後のテスト**
機械学習の前処理を変えた場合は、統合の前後でテストを実行しましょう。コードとして整合していても、予測値が意図しない形に変わる可能性があります。

### 29. GitHubと共有する基本操作

**このページの目標：** clone・remote・push・pullの意味と実行順序を理解する

GitHubはGitのコミット履歴を他者や別のPCと共有する場所です。

#### リモートの状態を確認
```bash
git remote -v
git branch -vv
```
リモートのURLとブランチの追跡設定を確認します。設定がないリポジトリでは何も表示されないことがあります。

#### GitHubの既存リポジトリを取得
```bash
git clone https://github.com/your-account/git-practice.git
```
`your-account`は自分のGitHubユーザー名に置き換えます。実在するリポジトリURLが必要です。

#### コミットをGitHubに送る
```bash
git push -u origin main
```
`-u`は以降のpush/pullに利用する追跡先を設定します。リモートが未登録なら `git remote add origin <URL>` が必要です。

#### リモートの更新をローカルへ反映
```bash
git fetch origin
git pull --ff-only origin main
```
`fetch`はリモートの情報を取得、`pull`はローカルの現在ブランチへ取り込みます。`--ff-only`は履歴をfast-forwardできる場合に限って実行します。

**補足／注意：混乱しやすい点**
`git pull`はGitHubに送るコマンドではなく、GitHubなどから更新を取り込むためのコマンドです。

### 30. 履歴を消さずに過去のコードを扱う

**このページの目標：** show・restore・revertの使い分けを具体的に説明できる

動いていた時点のコードを確認したい場合と、誤った変更を取り消したい場合では操作が異なります。

#### 過去のコードを読む（変更しない）
```bash
git show a1b2c3d:train.py
git diff a1b2c3d HEAD -- train.py
```
この2つは表示・比較が目的です。実行しても作業ディレクトリのファイルは基本的に書き換えません。

#### 過去版を作業ファイルへ取り出す
```bash
git restore --source=a1b2c3d -- train.py
git status
```
実際のコミットIDに置き換えます。作業ディレクトリのtrain.pyを過去版で置き換えるので、編集内容を失うおそれがあります。

#### 共有済みの不具合コミットを取り消す
```bash
git revert <取り消したいコミットID>
```
通常は取り消しのための新しいコミットを作ります。衝突がある場合は手動の解決が必要です。

**補足／注意：初心者が避けたい操作**
`reset --hard`や履歴のforce pushは、別の目的を持つ強い操作です。今回は「見る」「作業ファイルへ取り出す」「新しいコミットで取り消す」を区別できれば十分です。

### 31. Gitに入れないデータと秘密情報

**このページの目標：** 除外設定を理解し、モデル・ログ・認証情報を誤って公開しない

機械学習プロジェクトは学習データ・モデル・一時ファイルが大きくなるため、Gitへ追加する範囲を決める必要があります。

#### 典型的な.gitignore
```gitignore
# 秘密情報
.env

# Pythonの一時ファイル
__pycache__/
.pytest_cache/

# 大容量データ・学習成果物
data/raw/
artifacts/

```
必要な設定ファイルやデータの保存方針はプロジェクトに合わせて調整します。

#### 記録する必要がある情報とGit管理は別
学習データやモデルをGitから除外しても、実験の再現に必要な情報を管理しなくてよいわけではありません。データの取得元、スナップショット、環境、MLflowのRunなどは別途記録します。

#### すでに追跡していたファイルを追跡対象から外す
```bash
git rm --cached .env
git commit -m "認証情報ファイルの追跡を解除"
```
`.env`の実ファイルは作業フォルダに残しつつ、次のコミットからGitの追跡対象を外せます。ただし過去の履歴から秘密情報は消えません。

**補足／注意：秘密情報が履歴に入った場合**
GitHubへ公開してから `.env` を削除しただけでは、過去コミットに残る場合があります。該当の認証情報を無効化・再発行し、必要に応じて履歴の除去と公開状況の確認を行う必要があります。

### 32. DemandPilotで特徴量を追加する

**このページの目標：** 現実の開発でなぜGitの各操作が必要になるか一連の作業で理解する

ここではDemandPilotの需要予測コードに新しい特徴量を加える流れを想定します。実プロジェクトを直接変更せず、考え方を確認する例です。

#### 作業の前提
すでに `main` には動作確認済みのコードがあり、GitHubへ共有されているものとします。ここから新しい特徴量を追加し、モデルの精度を比較したい状況です。

#### 安全に進める標準的な流れ

mainの状態を確認 → 改善ブランチ → 編集・テスト → 変更を確定

- **mainの状態を確認：** git status / log
- **改善ブランチ：** switch -c
- **編集・テスト：** diff / pytest
- **変更を確定：** add / commit

検証・レビューが完了してからmainへ取り込みます。

#### 最初の確認と作業ブランチ
```bash
git status
git log --oneline -3
git switch -c feature/new-demand-feature
```
作業前に意図しない未コミット変更がないことを確認してからブランチを作ります。

**補足／注意：DemandPilotの実行環境**
DemandPilotのようにDockerでPythonを実行する構成なら、実際のテストもDockerコンテナ内で実行します。ここでのGitコマンド自体は通常ホストPCから操作します。

### 33. 変更・テスト・コミットを一連で実行

**このページの目標：** 複数のGit操作を組み合わせて、意味のある変更履歴を残せる

特徴量を加えた後、すぐにコミットせず差分とテストを確認します。

#### コード変更とテストが1セット
例えば「販売数量の直近7日平均」を特徴量に加える場合、その計算式だけでなく、データリークを起こしていないか確認するテストも必要になります。コードと関連テストを同じ目的のコミットにまとめます。

#### 実行手順の例（説明用）
```bash
# src/features.py を編集し、tests/test_features.py を更新
git status
git diff -- src/features.py tests/test_features.py

# Docker運用の場合のテスト例
docker compose run --rm --entrypoint pytest pipeline -q

# 変更内容をステージして確認
git add src/features.py tests/test_features.py
git diff --staged
git commit -m "需要予測の特徴量を追加"
```
上記のDockerコマンドはDemandPilotで使っているCompose構成を想定した例です。テストの実行後にコミットします。

#### なぜすぐcommitしないのか
動作確認前のコードも履歴に残せますが、機械学習では前処理や評価期間を誤ると数値だけが良く見える場合があります。少なくともテスト結果・意図しない差分の有無を確認してからコミットすると、履歴の意味が明確になります。

**補足／注意：履歴から確認できること**
このコミットには、特徴量の実装とテストの変更が含まれています。後日、評価の変化を調べる際に `git show <コミットID>` を使って「何を変えたか」を確認できます。

### 34. 学習条件とコードのバージョンを記録

**このページの目標：** GitのコミットIDを実験記録と紐づける意味を説明できる

改修後のコードで複数のパラメータを試すと、Gitだけでは「どの実験が何を出したか」までは管理できません。ここからMLflowと役割分担します。

#### 学習前にコミットIDを確認
```bash
git status
git rev-parse HEAD
```
最初に `git status`で未コミット変更がないことを確認します。`git rev-parse HEAD`は現在参照しているコミットのIDを表示します。

#### 実験とコードの対応（数値は架空）
| Gitコミット | MLflow Run | 学習率 | MAE |
| --- | --- | --- | --- |
| `f3a91bc` | Run 001 | 0.01 | 280 |
| `f3a91bc` | Run 002 | 0.001 | 260 |
| `f3a91bc` | Run 003 | 0.0001 | 267 |

#### なぜGitコミットが同じでも良いのか
学習率は実行時のパラメータとして変えられるため、学習コードを変更しなければGitの履歴は増えません。一方MLflowのRunは実験のたびに別のIDを持ち、学習条件・精度・学習済みモデルなどを管理できます。

#### Docker内でGitコミットIDを渡す例
```bash
# MacなどGitがある作業PC側
GIT_SHA=$(git rev-parse HEAD)
docker compose run --rm -e GIT_SHA="$GIT_SHA" pipeline train

# Pythonの学習処理側（考え方）
# mlflow.set_tag("git_commit", os.environ["GIT_SHA"])
```
この例はGitHub Pagesで動くものではなく、ローカルDocker/MLflowを組み合わせた運用例です。Python側で明示的なタグ記録処理が必要です。

**補足／注意：コンテナの場合の注意**
Dockerイメージに `.git`を含めていない場合、学習プロセス内ではコミットIDを自動取得できないことがあります。ホスト側でコミットIDを取得し、環境変数などでコンテナへ渡す方法があります。

### 35. 精度が悪化した原因を追う

**このページの目標：** MLflowのRunから対応するコードを特定する調査手順を説明できる

モデルのMAEが悪くなったとき、まず「学習コードを変えたのか、実験条件が変わったのか」を切り分けます。

#### 不具合・精度悪化時の調査

MLflow → Git → 差分確認

- **MLflow：** Runの条件と評価
- **Git：** Runに対応するコミット
- **差分確認：** 変更内容を比較

データ期間、ライブラリ、乱数などの条件も合わせて確認します。

#### 同じGitコミットの場合
同じコミットのRun間で精度が変わったなら、まず学習パラメータ、使用データ、データの分割、乱数シードなどを確認します。コードが同じでも、実行条件が違えば結果は変わります。

#### 異なるGitコミットの場合
精度の差がある2つのRunに異なるコミットIDが記録されているなら、Gitでコードの差分を確認します。例えば特徴量のウィンドウ幅、対象期間、欠損値処理などが変更されていないか調べます。

#### 2つのコードの違いを確認
```bash
git diff <以前のコミットID> <現在のコミットID> -- src/features.py
git show <現在のコミットID> --stat
```
`<...>`は説明用の置換箇所です。実行時には実際のコミットIDを指定します。

### 36. GitHubへ公開・共有する

**このページの目標：** ローカル変更が公開サイトへ届くまでの流れを説明できる

改修が完了したら、ローカルの履歴をGitHubに送ります。これで他者がコードを参照したり、GitHub Pagesでサイトを公開したりできるようになります。

#### コミット済みの変更を確認
```bash
git status
git log --oneline -3
git remote -v
```
push先のURLが正しいことを確認します。別リポジトリへ誤って送信しないためにも重要です。

#### リモートへpushする
```bash
git push -u origin feature/new-demand-feature
```
改善ブランチをGitHubに送る例です。mainへ統合する前にプルリクエストを作成してレビューする運用もあります。

#### GitHub Pagesの場合
Web教材のような静的サイトなら、GitHubの対象ブランチへHTML・CSS・JavaScriptなどをpushした後、GitHub Pagesのデプロイ処理によって公開ページへ反映されます。単なるGit commitと、Webページの公開は異なる段階です。

**補足／注意：公開前に必ず見るもの**
GitHubのPublicリポジトリは第三者がコードやコミット履歴を確認できます。秘密情報・社内ソース・個人情報・ライセンス条件に問題がないか、push前に確認してください。

### 37. 全体を1枚で振り返る

**このページの目標：** Gitの目的・概念・操作をつなげて説明できる

Gitで重要なのは、コードをどの時点で記録しているかを整理することです。

#### 変更が履歴になるまで

編集 → git add → git commit → git push

- **編集：** 作業ディレクトリ
- **git add：** ステージング
- **git commit：** ローカルの履歴
- **git push：** GitHubへ共有

履歴を確認するときはlog/show/diff、別の作業を試すときはswitch/mergeを使います。

#### 何がしたい？→どのコマンド？
| やりたいこと | 主なコマンド |
| --- | --- |
| 現在の変更状態を知る | `git status` |
| 未ステージの差分を知る | `git diff` |
| 次のコミットに入れる | `git add` |
| 変更を履歴として残す | `git commit` |
| 履歴を一覧で見る | `git log` |
| 過去の中身を見る | `git show` |
| 別の改善を始める | `git switch -c` |
| 別のブランチを取り込む | `git merge` |
| 共有済みの修正を打ち消す | `git revert` |
| GitHubへコミットを送る | `git push` |

#### Gitと他の技術の関係
Gitはコード履歴、Dockerは実行環境、pytestは動作確認、MLflowは実験とモデルの記録を主に担当します。機械学習の再現性を高めるには、これらを組み合わせて使う必要があります。

## 知識問題（最後にまとめて実施）

### 問題01. Gitでローカルのコミットを作ると、自動的にGitHubの公開サイトも更新される？

- A. はい。commitするとすぐ更新される
- B. いいえ。通常はpushなどが必要
- C. ブランチを作れば必ず更新される

**正解：B**  git commitはローカルの履歴を作る操作です。GitHubへ送るには通常git pushが必要です。

### 問題02. 新しく作成したtrain.pyをGitの管理対象に入れる前の状態は？

- A. 通常は未追跡（Untracked）
- B. すでにコミット済み
- C. 自動的にステージ済み

**正解：A**  新規ファイルはgit addするまで原則として未追跡です。

### 問題03. 作業ディレクトリ・ステージング・コミットの順に相当する操作は？

- A. commit → add → 編集
- B. 編集 → add → commit
- C. push → commit → add

**正解：B**  まずファイルを編集し、addで対象をステージして、commitで履歴に確定します。

### 問題04. train.pyをaddした後、さらに編集した。次にcommitすると基本的にどの内容が入る？

- A. addした時点の内容
- B. 最後に編集した内容が必ずすべて入る
- C. どちらも入らない

**正解：A**  addした時点でステージした内容が対象です。後から編集した分は再度addしないと通常コミットに入りません。

### 問題05. ステージ済み内容と直近のコミットの差分を見たいときは？

- A. git diff --staged
- B. git log --oneline
- C. git push

**正解：A**  git diff --staged（--cachedも可）はステージングとHEADの差分を表示します。

### 問題06. ある時点の追跡ファイル全体の構造を表すGitオブジェクトはどれ？

- A. Blobだけ
- B. Tree
- C. HEADというソースコードファイル

**正解：B**  Blobは内容、Treeは名前とフォルダ構造との対応、CommitはTreeと履歴情報を保持します。

### 問題07. Gitのブランチについて正しい説明は？

- A. 必ずファイル一式を新しいフォルダに複製する
- B. コミットを指す名前付きの参照である
- C. GitHubでしか使えない

**正解：B**  ブランチはコミットを参照する情報です。ローカルGitだけでも利用できます。

### 問題08. HEADは通常何を示す？

- A. 現在選択しているブランチ
- B. 最も精度が良いモデル
- C. 直近のMLflow Run ID

**正解：A**  通常HEADは現在選択中のブランチを示し、そこからコミットを参照します。

### 問題09. すでに追跡中の.envを.gitignoreに追加すると、過去の履歴から秘密情報が消える？

- A. はい。全履歴から消える
- B. いいえ。追跡や履歴の除去には別対応が必要
- C. GitHub Pagesだけから消える

**正解：B**  .gitignoreは未追跡ファイルの追加除外が中心です。追跡済みファイルや過去履歴は消しません。

### 問題10. 未コミットの編集を残したまま、ステージだけ解除したいときは？

- A. git restore --staged train.py
- B. git reset --hard
- C. git push

**正解：A**  git restore --stagedはステージ側の状態を戻し、通常は作業ファイルの変更を保持します。

### 問題11. 共有済みの不具合コミットを、履歴を消さずに打ち消したいときの代表的な操作は？

- A. git revert
- B. git init
- C. git diff

**正解：A**  git revertは新しい取り消しコミットを作り、共有された履歴を保持します。

### 問題12. mainが分岐以降に変わらず、featureだけ新しいコミットを積んだ。単純にmainへ取り込むと？

- A. fast-forwardできる場合がある
- B. 必ずコンフリクトする
- C. リモートを必ず削除する

**正解：A**  mainの参照先をfeatureの先端に進めるだけで統合できる場合があります。

### 問題13. 同じGitコミットで学習率を変えて3回実験した場合、MLflowのRun IDは？

- A. 同じコミットならRun IDも同じ
- B. 3回の実験で別々のRun ID
- C. Gitのブランチ名と等しい

**正解：B**  Gitコミットはコードの状態、MLflow Runは1回の実験を識別します。

### 問題14. Dockerイメージから.gitを除外した場合、コンテナ内でGitコミットIDを自動取得できないことがある。対応例は？

- A. ホスト側でコミットIDを取得して学習処理へ渡す
- B. モデル重みをGitHubへ必ず登録する
- C. GitHub Pagesを停止する

**正解：A**  ホストでgit rev-parse HEADを実行し、環境変数や実験タグを通じて学習プロセスに渡せます。

### 問題15. 精度の悪化を再現・分析するために、Gitコミットだけで十分？

- A. 十分。Gitのコードだけで必ず再現できる
- B. データ・依存環境・パラメータ等も必要
- C. GitHubの星の数があれば十分

**正解：B**  コードが同じでもデータ、乱数、ライブラリ、学習条件などで結果は変わります。これらの追跡も必要です。
